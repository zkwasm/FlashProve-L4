# Published works that the code implements

This page lists published papers, books, standards, manuals, documentation and posts, and some works that are not published, whose methods the programs, scripts and Lean files of this repository implement, follow or cite, with the files that apply or name each. Its last section lists the works that the files name; a work that a file names in an unusual way can be missing there. Whether each cited theorem, section or page says what the comment or this page takes from it has not been checked. It speaks of ideas, methods and formats. Code, text, values and fonts of others that are in this repository are listed, with the copyright lines and licences that their entries give, in THIRD_PARTY.md, NOTICE and lean/CREDITS.md; docs/sources-notes.tsv lists most of them file by file.

What the labels in the tables and in the sources' comments mean ("source for", "follows", "the idea is public" and the like) is said under "Published methods of the proof system".

## The paper that this protocol builds on

A. Chiesa, G. Fenzi, G. Weissenberg, "Zero-Knowledge IOPPs for Constrained Interleaved Codes", revised version, 2026; an earlier version: Cryptology ePrint Archive 2026/391. The library `blocks/` implements its proximity test, with the zero-knowledge sum-check, the code switch and the last step of which the test is made. Where the masking here differs from the paper's, so that its results on hiding do not carry over by themselves: docs/limits-all-rows.tsv, row H1.1. A file that restates a definition, a construction or a lemma of the paper says so in a comment with the word "Follows", "follow", "follows" or "restates". "Nothing is listed" or an empty cell means that the files were not compared with the paper on that point, not that nothing is owed or nothing differs. "A difference is not listed here" says that the files differ from the paper on that point and that this page does not tell how. "Further work that this protocol builds on", in one cell of the first table, is further work of the three researchers whom README.md's acknowledgments name first.

## A published method

Karvonen, Reuter, Rinberg, Marks, Garriga-Alonso, Warr, "DiFR: Inference Verification Despite Nondeterminism", arXiv:2511.20621, is cited for the two acceptance policies under which a proof can be made. The clipped-gap score follows the score of Token-DiFR at temperature 0: the margin of the served token to the top score, clipped, averaged and compared with a threshold (the margin: section 4.2, eq. (1); the clip: 4.2; the mean: 5.2; the threshold: 4.1; the use at temperature 0 without a shared seed: 7.2, with a case study in appendix D). The other policy, exact match, asks that each counted token is the argmax of the logits at its position; the source for that check is the same paper (section 7.2; appendix A, "Exact-match variant"). prover/head/forward.cuh cites the paper for the clipped-gap score, and so do guide/how-it-works.md, docs/architecture.md, integrations/vllm/README.md and integrations/vllm/REFERENCE.md. integrations/vllm/integer_model/README.md links the paper for the scoring of a served reply in a prefill pass, which is the paper's section 3.3; integrations/vllm/integer_model/integer_model/noise.py and docs/model.md cite its sections 3.2 and 4.2; and the docstring of integrations/vllm/integer_model/examples/fit_limits.py names it for the percentile of the clip (section 5.2) and for a threshold that is taken from a calibration set of honest runs (section 4.1). A third rule, which is in the code and which no program takes, scores a token by its negative log-probability under a softmax of the model's logits: that score is the same paper's "Cross-entropy Baseline" (section 4.2).

The clipped-gap score here differs from the paper's in four ways:

- ties count: 1 is added to the margin if the entry with the top score has a lower index than the served token;
- one known offset, 2^sh, is added at each position (`sh` is a line of the parameter file);
- there is a bound on the number of clipped positions;
- the threshold is a line of the parameter file (`theta`), set by the party that makes the commitment; the programs that make and check a proof do not calibrate it.

## Published methods of the proof system

**What the labels mean.** Comments in the sources and the tables below use these words. "Source for", "Source:", "Public source", "follows", "follows the way of", "has the form of" and "is the protocol of" name the published work in which a step is stated. "In the line of", "a related technique", "related work" and "see also" name published works on the same subject. "The idea is public" names a work that states an idea which the code also has. "Named through" says that a work is known here from another work's account of it alone. "Ours", "our own" and "Of this file's own" say that a step came from this project's own work, or how it differs from the work named beside it; they claim neither that the step is new nor that it follows nothing older. In the tables' cells a sentence tells the work's side, as this page reads it, if it begins with "There" or with "In" and the work or a part of it ("In the paper", "In zkGPT", "In section 5 of the paper"), or if its subject is the work, its authors, or a part, a statement or a party of it; so do the sentences that follow such a sentence, up to the next one that speaks of this repository ("Here", "here", or a file, a routine or another name of this repository). "This protocol's technical report" is a write-up of this project's own that is not in this repository. For most places it is not known whether the code was written from the named work. Under `prover/` many labels and web addresses name a public source that has the method; they do not say that the code was written from it.
