# The audit with the secret key

*No comparison of this page with the scripts in this folder or with the programs' sources is known,
and parts of it may have been written for [other sources](../../docs/glossary.md#other-sources).*

## What it is for

A verifier cannot tell whether a published file hides anything. If a bug makes the random masks zero, leaves out a salt, or uses one mask twice, everything still verifies. This tool checks from the provider's side: it takes the public files and the provider's secrets, recomputes every published value that is pure randomness, and compares byte for byte. It never says «hidden»; it says «each of these values is what the rule gives».

Its main use is to audit a **commitment** (the key file `<public>/key.bin` and one entry `<public>/leaf/<k>.bin` for each stored copy of the weight table) before it is handed out. Its second use is to audit **one batch of proofs** that the default build has made for this purpose. Other terms: `docs/format/FORMAT.md`.

**Every call that is given a secret folder accepts only commitments to synthetic weights (docs/glossary.md),** and `cp_commit` refuses the option below on real weights. So this rehearses the procedure. Each of the two refusals is one `if` in its program, and `cp_prove` refuses to start on a secret folder while anything is in its `audit/`. That check only sees whether the folder is empty, not whether a YES was said: beyond it no program keeps `cp_prove` off a folder whose audit has not passed. `cp_prove` refuses its own option of that name on real weights as well («Audit one batch of proofs»).

## Try it

Build with the test options (g++ 13, CUDA 13.2 Update 2, python3 with numpy, one H100; a later CUDA toolkit is not supported: [prover/docs/build.md](../../prover/docs/build.md)):

```sh
verifier/build.sh --field 2
prover/build.sh --field 2 tests
W=$(mktemp -d) && WORK="$W/audit" && echo "WORK=$WORK"
tools/audit/play.sh prover/build/hc/test_build 2 "${WORK:?first run the line with mktemp}"
```

(The programs are in `prover/build/hc/test_build`. The work folder must not exist yet; its path may contain only letters, digits, "/", ".", "_" and "-", and no part of it may be ".." or begin with "-".) The second line builds three programs one after another: more than half an hour on the machines that it was tried on, with little on the screen but compiler warnings, which a good build has too. The last line: in about ten minutes it makes a small commitment and two batches of proofs under a seed of its own and a second commitment under a drawn seed, audits them, and runs the tool's self-tests. Three steps destroy kept files that the script has made itself in its work folder: the five of the two commitments, and the second batch's one, which it writes again for each scene. The script itself removes, by their names, a few files that its own scenes have put into that work folder. The last line must read `audit play: field 2: ALL AS EXPECTED`. The folder above the new work folder must exist, and no other account may be able to change a place above it (as for the work folder of the audit, below).

## Audit a commitment before you hand it out

The calls below name `cp_commit`, `cp_prove` and `cp_verify` without a path: after `verifier/build.sh` and `prover/build.sh` the three lie in `prover/build/hc/`. The paths that begin `tools/` are written from the tree's top; `>> audit.log` adds to a file of that name in the folder where you stand.

1. Make it with the option `-keep-for-the-audit`:
   `cp_commit -weights made-up-blocks -config <config folder> -M <entries> -ivk <public folder> -isk <secret folder> -keep-for-the-audit`.
   That keeps, in `<secret folder>/audit/`, the 32 random bytes that went into the key file and into each entry. Together with the seed they open every mask in the public files, so they must not outlive the audit.
   `cp_commit` makes both folders itself: neither may exist yet, and the folder above each must exist. It opens that folder from `/`, one part at a time, and refuses the call at once (`cp-commit-path`, status 2, nothing touched) if a part of the way is a link, belongs to an account other than yours or root (for root under `sudo`, the account that ran `sudo` counts as yours too), or can be written by its group or by others and has no sticky bit. We know this from reading the code.
2. When `cp_commit` has ended well, on the same machine and account, before anything leaves and before any `cp_prove` is started:

```sh
W=$(mktemp -d) && WORK="$W/audit" && echo "WORK=$WORK"
tools/audit/audit_commitment.sh <public folder> <secret folder> "${WORK:?first run the line with mktemp}" --rehearsal >> audit.log 2>&1; echo "status $?"; tail -n 1 audit.log
```

That call is a rehearsal: all the checks, and nothing is destroyed. Only after `status 6`, the audit itself, once:

```sh
tools/audit/audit_commitment.sh <public folder> <secret folder> "${WORK:?first run the line with mktemp}" --erase-kept-files >> audit.log 2>&1; echo "status $?"; tail -n 1 audit.log
```

- **Go by the status,** not by a search for «YES»: other last lines contain that word too. Do not pipe the output into `tee` or `head`.
- **Nothing is destroyed or erased unless the last word is `--erase-kept-files`.** With `--rehearsal` the call is a rehearsal: the same checks, and the kept files stay. A call without a last word is refused (status 2), and nothing is looked at: so a word that gets lost (an empty variable without quotation marks) starts nothing. A call that has one of the two words in a folder's place is refused too, and so is every call with an empty word. A rehearsal is no audit: until the call with `--erase-kept-files` has said YES, nothing of the commitment may leave.
- The work folder gets the tool's helpers (two to three minutes the first time; the audit itself takes seconds at the small sizes). Name a work folder that does not exist yet, or one in which only you can write; the same one can be used again. One audit at a time works in a work folder, and nobody should work in the tree meanwhile.
- No other account may be able to change a place above the work folder or the secret folder, and the group and others must have no permission on the secret folder. For the public folder, which is only read, no folder or link on the way may belong to an account other than yours or root. Otherwise the call is refused (status 2, the place by name, nothing read or destroyed). Name the folders from `/`.
- After such a refusal the kept files are still there, and `cp_prove` goes on refusing the secret folder: if you know that since you committed no other account could write there, close the place that the refusal names to others, if it is yours, and run the audit again; otherwise the commitment is in doubt (docs/faults.md, on `cp-isk`): make it again in a place below folders that only you or root can change.
- Whoever can write an open folder on the way to the public folder (or to a batch's requests or responses) cannot make a YES, but can turn an honest audit into a NO or a NOT WHOLE, which for a batch erases the kept file: keep these folders, too, where nobody else can write.
- Give the two folders as they are. **Never copy a secret folder for an audit:** each folder counts how much of its tables it has shown, and hiding holds only up to a limit; two copies each count alone. And the audit would destroy only the copy's kept files.
- One audit at a time on a folder.
- **Under `sudo`.** Do not run any of this under `sudo` or as root. A known fault: the account that ran `sudo` counts as yours only on the way to a folder. The work folder itself and `<secret folder>/audit/` must belong to the caller, who under `sudo` is root. So a work folder that your own account made is refused (status 2). On a commitment or a batch that your own account made, the audit ends NOT WHOLE (status 4, "isk/audit/ is not a folder of mode 0700 that belongs to the caller"), even if nothing is wrong with the files. Nothing is erased or destroyed, with `--erase-kept-files` too: a batch's last line then says THE ERASURE STOPPED. Under `sudo` a NOT WHOLE with these words says nothing about the files: run the audit again as the account that ran `cp_commit` and `cp_prove`, with a work folder that does not exist yet, and go by that verdict. Until then nothing of that commitment leaves the machine. A NOT WHOLE with other words is no exception. For its verdict the audit needs nothing that only root has; where your account may not lock enough memory it prints MEMORY NOT LOCKED ("Memory and media"). We know this from reading the code.

| status | the last line contains | what it means | what to do |
|---|---|---|---|
| 0 | YES | every check passed, no prover has run on the folder, and the kept files have been overwritten and removed | keep audit.log: the digests and the ID in it are not printed twice; compare them with what you hand out. (Under a test seed the line adds: nothing is hidden, not to be handed out. Under a public seed, which `cp_commit` does not take together with `-keep-for-the-audit`: nothing is hidden) |
| 1 | NO | a check failed (each kind is a line `CRY: ...`), or a prover has run | **Stop and tell the person in charge.** Nothing of this commitment may leave, and nothing is served from it. No tool removes a commitment: keep both folders closed |
| 4 | NOT WHOLE | a kept file is missing, foreign, linked or has other permissions; a public file is missing or extra; or the removal was stopped part way | as for NO (under `sudo`: see "Under sudo" above) |
| 5 | NOTHING KEPT HERE | «no folder»: made without the option, cannot be audited. «empty»: after a YES nothing to do; before one, as for NO | do not run `cp_commit` into the same folders again |
| 6 | REHEARSAL PASSED | the checks passed; nothing was destroyed; no digests are printed | run it with `--erase-kept-files` |
| 2 | refused | a mistyped call; a call without a last word; a folder's name that begins with «-»; a secret folder that is, or lies below, a place that another account may be able to change, or on which its group or others have any permission; a part of a folder's path that is not there; a folder or a link of another account's on the way to the public folder; helpers in the work folder that are not yours alone, or a link there; a work folder inside one of the two other folders, or one that holds one of them, or whose parent does not exist, or below a place that another account may be able to change; weights that are not made up; `<secret>/leaf/<k>/fresh.bin` is missing (running it again does not help); core dumps cannot be switched off | |
| 3 | | a helper could not be built, or g++, python3 or numpy is missing (numpy must come from the system's packages or from a virtual environment: the scripts start python3 so that `PYTHONPATH` and your user site-packages are ignored) | |
| 7 | NO VERDICT | the tool stopped; the line says whether a kept file was touched | if none was: fix the cause and run again; else as for NO |
| other | | killed: no verdict | run again; it may now say NOT WHOLE. If the kill fell while the kept files were being destroyed, no later run destroys the rest: that commitment has no YES and is not handed out: make it again, and tell the person in charge of the files that are left |

**The only files that this command ever removes** are `audit/key.fresh` and `audit/entry.<k>.fresh` in the secret folder that you name, and only in a call with `--erase-kept-files`, after every check has passed (`kept.py`). If it is stopped while removing, some are gone, the last line says how many, and it counts as NO. In every other case they stay beside the seed, together with which they open every mask in the public files (step 1): nothing of the commitment may leave, and `cp_prove` refuses the folder. At a NO or a NOT WHOLE, tell the person in charge.

### What a YES covers

In the key file and every entry: the random bytes of the hash chains; the salt of every opened leaf; every opened value of every mask row; the masked words of the last step of each proximity test (one of the four, the masked main message, is not recomputed: the recomputed mask is taken off, and what is left is compared with the committed row at its opened positions); all hiding sums; the hash trees that consist of random values only (three in the key file), rebuilt whole; and the answers to the samples of messages of such values (two in the key file). If one of these trees or answers were skipped, the audit would report it, but not at `--level=0`; under `--batch` a skip is reported only for those in proofs, and under `--drawn` for none.

### What a YES does not cover

1. **Proofs.** A YES is about the commitment's public files only. A proof made without test options can be audited only if its batch was made for that («Audit one batch of proofs», below): the random bytes of every other batch are kept nowhere. With `--drawn` (below), a prover that draws no pads at all is not noticed.
2. **Pads that lie inside tables of real values** (two in the key file, two in each entry; one more at the small sizes). A committer that draws such a pad and does not put it in place passes these same checks; the answer that it should mask is then a plain linear form of real values. Likewise random entries of such a row that are passed on correctly but not encoded. And the random values that fill a proximity test's main rows after the folded row: the programs draw and use them, and no comparison reads them; without the programs' own list of draws, which a default build does not write, nothing checks them or the lengths of their draws.
3. **The stored weight tables' columns,** and leaves that no opening reaches in trees that hold real values. Checking these needs the weights («level 2», not part of this repository). A row is checked through its code word at the opened positions only: a false pass has chance at most ((message + random entries - 1) / length)^positions, for a faulty program, not for an adversary. A salt is compared only where its leaf is opened: a fault in a share s of a tree's leaves is missed with probability (1 - s)^positions, so a fault in one leaf is almost always missed.
4. **Bugs that this tool shares with the programs.** The order of the random draws was read from the prover's source; some parameters come through the verifier's own code; for key file and entries, prover and verifier share the routines that say which entry masks what. A build without test options writes no list of its draws, so their order, and the length of a draw that enters a compared value whole, are checked only through the compared values. And a comparison by value cannot see a word of a random value's label that is zero, or equal to another word, in every run that is compared: a program that left such a word out, or put one in the other's place, would write the same files. Which words they are in the runs that this tool has compared has not been worked out.
5. **The configuration.** It audits against the configuration in the secret folder. Whether that is the one you meant, check by the printed ID.
6. **Whether a mask is applied** to the value that it should hide. `cp_commit` writes no public file before the verifier's code has passed it; this tool does not ask again. Nor does it ask whether a random value has a second use at a place that is not compared, or whether a file holds another function of it than the format says.
7. **Whether something has already left.** It only sees that no prover has counted an opened column in this folder.
8. **Memory and media.** It is Python: it zeroes the buffers into which it reads the kept bytes, but cannot wipe every copy. Where it prints MEMORY NOT LOCKED, secrets may reach swap. «Removed» means overwritten, synced and unlinked; that does not reach journals, flash or snapshots.
9. **The pads of a stored table's record.** The programs, their files and the format say "the record" for a table's published out-of-domain (OOD) answers (masked sums of the weights). They say "the record's seeds" for its OOD seeds ([glossary](../../docs/glossary.md#record)). The key file and each entry hold, after the table's root, the record's answers: each answer is a weighted sum over a row's real entries plus a public factor beta times a pad (three random values in places of the row's message beside the weights, read as one element). The audit recomputes none of these answers. Beta and the pad could be recomputed from the key, but what is left when they are taken off is a value of the weights, which the audit does not have. **So a committer that leaves the pads out gets a YES, and each published answer is then one exact linear equation on a row of the weight table.**

   What is seen without any secret: an answer that is 0, or that appears twice (pads missing on rows that hold no weight, or on equal rows); no other missing pad. Beyond that these bytes are parsed, and they enter the replayed chains, the ID and two keys (class `record-answer`, level 0). Both audits have said YES, at small size and at full size («What has been run»): as the YES line says itself, that says nothing of these pads.

## Audit one batch of proofs

Every mask, pad and salt in a batch's proofs follows from the seed and from 32 bytes that `cp_prove` takes from the operating system when the batch begins. These bytes are normally kept nowhere, so nobody can recompute a proof's random values. `cp_prove -keep-for-the-audit` keeps them for one audit, in `<secret folder>/audit/batch.fresh`. This is how a production build, under seeds that it drew itself, can be checked by value.

**While that file exists, hiding is void for the batch:** whoever reads the secret folder can open its proofs. So the option is for a batch of your own requests, made for the audit; `cp_prove` refuses it in a service (`-spool`) and on real weights.

1. Audit the commitment first (above). `cp_prove` refuses a secret folder while anything is in `audit/`, so the two audits never overlap.
2. Make one batch from a folder of request files (`<name>.req`: T tokens, then r and e, as little-endian 32-bit words, with T = 2^`lt` of the parameter file; `prover/tools/make_request.py <policy.txt> <request file to write>` writes one with made-up tokens): `TMPDIR="${W:?first run the line with mktemp under Audit a commitment before you hand it out}" cp_prove -isk <secret folder> -in <requests> -out <new folder> -keep-for-the-audit`. Give `-isk` and `-out` the folders' whole paths, from `/`. The default build's `cp_prove` also wants `HOME` and `TMPDIR` set, each to a folder that exists, by an absolute path (its usage text has the rule); `TMPDIR` is unset in most shells, and the call is then refused (`cp-prove-environment`): so the call above gives it `W`, the folder that the line with `mktemp` drew. Give it only folders that nobody but you can read or write. The commitment's audit prints an ID (`audited: the ID ...`), which it works out from the configuration in the secret folder and the key file: it must be the ID that `cp_commit` printed when it made the commitment (its line `commitment ID: ...`).
3. When `cp_prove` has ended, on the same machine and account, before any response is handed out and before any other `cp_prove` is started, with the folder of requests exactly as `cp_prove` read it (`WORK` is the work folder that you drew under "Audit a commitment before you hand it out"; in a new shell, run that line with `mktemp` again: the helpers are then built again, two to three minutes):

```sh
tools/audit/audit_batch.sh <public folder> <secret folder> <requests> <responses> "${WORK:?first run the line with mktemp under Audit a commitment before you hand it out}" --rehearsal >> audit.log 2>&1; echo "status $?"; tail -n 1 audit.log
```

That call is a rehearsal. If it ends with 1 or 4, do as the table says for that status; `batch.fresh` is still there, and the call with `--erase-kept-files` erases it at its verdict, unless its last line says otherwise. Only after `status 6`, the audit itself, once:

```sh
tools/audit/audit_batch.sh <public folder> <secret folder> <requests> <responses> "${WORK:?first run the line with mktemp under Audit a commitment before you hand it out}" --erase-kept-files >> audit.log 2>&1; echo "status $?"; tail -n 1 audit.log
```

4. Run `cp_verify` on every response as well: this tool does not ask whether a proof verifies.

What is said above about the status, the work folder (the same one can be used), where the other folders may be (the requests and the responses are treated as the public folder is) and copies of a secret folder holds here too. What differs:

- **Responses may be handed out only after a YES and `cp_verify`'s acceptance (step 4),** not merely once the file is gone: a NO and a NOT WHOLE erase it too, unless the last line says otherwise.
- **In a call with `--erase-kept-files`, `batch.fresh` is erased at every verdict: YES, NO or NOT WHOLE** (unless it is left alone: the next point), also where the tool stops over an error of its own. (A public folder, requests' folder or responses' folder that is not there, a mistyped name for one, is refused before that: status 2, nothing erased.) A batch can be made again; but after a NO or a NOT WHOLE the commitment itself counts as in doubt, and nothing of it may leave the machine (docs/operators-duties.md, "The audit with the key"). The file must not outlive its one audit. That is why the rehearsal comes first: the same checks, and nothing is erased.
- **It is the only file that this command ever removes.** It is overwritten, synced and unlinked, and only if it is a regular file of yours, of at most 32 bytes, with one name (its mode and that of `audit/` are not asked here: a `batch.fresh` of another mode, or shorter than 32 bytes, is erased too, under NOT WHOLE); a hard link is left alone, because overwriting it would change the bytes under its other name. And only if it is still the file that the audit looked at when it began: if the file was moved away, replaced or changed while the audit ran, or `audit/` belongs to another account than the caller ("Under sudo", above), nothing is touched, the line says THE ERASURE STOPPED, and there is no YES, because the 32 bytes may live on under another name. Any other name in `audit/` is left alone and printed, and `cp_prove` goes on refusing the folder while anything is there.
- **The slots come from the folder of requests.** The batch's first key reads every slot: the request's words, or «no request» for a file that is not well formed (wrong length, a token outside the vocabulary, a bad range). Slot j is the j-th name in bytewise order, compared without `.req`. Nothing that is kept ties that folder to the batch. **If a file was added or removed in both folders, or renamed so that the order changes, or a failed request's file was changed so that other words or another «no request» follow, an honest batch gets a NO,** which cannot be told from a fault. A batch that was kept by a `cp_prove` built from a copy of the repository that differs from this tool's gets no YES either (from reading the code; not tried): take both from one copy of the repository. The audit prints the number of slots and one sha256 over their names and files.
- The key file and the entries are parsed, and their stored tables' salts are recomputed. Nothing else in them is: their own kept bytes are gone after the commitment's audit.

### What a batch's YES covers

In each proof: the number of the stored copy that serves the batch; the random bytes of the hash chains; the salt of every opened leaf, the stored copy's among them; every opened value of every mask row; the masked words of the last step of each proximity test (the masked main message as for a commitment); the hiding sums of the folds, of the links' look-ups and of the rows on the table; the hash trees that consist of random values only, rebuilt whole, and the answers to the samples of such messages; the proof's place in the tree that ties the batch together (the binding tree), its leaf's salt and its siblings. At the default setting that is 18.76 % of a batch's key file, entry and two proofs at the small size (18.78 % under a clipped-gap policy; 17.87 % where the commitment has two entries) and 7.66 %† at full size (one batch each). And over all files: no row is opened at more positions than it has random entries, no salt appears twice, no masked number is zero or appears twice.

### What a batch's YES does not cover

Points 2 to 9 of «What a YES does not cover» hold for proofs as well. Of these, point 6 rests for a commitment on `cp_commit`'s own pass through the verifier's code; for a batch it rests on `cp_verify`'s yes, which you have to ask for yourself (step 4). And point 7 holds more strongly: of whether a response has already been handed out, or another `cp_prove` has run on the folder, this audit sees nothing at all. In addition:

1. **The hiding sums of the sub-proofs' own rounds** (35 a proof at the small sizes, 185 at full size).
2. **Whether the 32 kept bytes are random.** The audit recomputes from whatever the file holds. A build whose call of the operating system gave zeros or a constant would get a YES.
3. **A well-formed request that failed.** If it got as far as its seal, that seal is a leaf of the binding tree, and no file holds it. The other proofs' siblings above the places that it may have taken are then not compared; their number is printed in a line of its own and in the YES line. For an audit that reaches everything, take a batch in which no well-formed request fails.
4. **Other batches.** A YES is about this batch. That the program treats a service's batches alike is not shown by it.
5. **Words of a label that are zero or equal in the batch that is compared** (point 4 of «What a YES does not cover»): in a batch of one request the slot's number is such a word.
6. **A retired copy whose secret folder is gone.** `cp_prove` allows that, though no call of `cp_commit` retires a copy. The salts of its table, which its entry opens, are then not compared; their number is printed in a line of its own and in the YES line.
7. **What has never been run** («What has been run»):
   - a commitment whose first stored copy in use is not copy 0 (no call of `cp_commit` makes one);
   - a faulty file at full size on the released programs, but for six copies with one bit changed, of the key file, the entry and one proof of each of two commitments, one to a real model's public weights and one to synthetic weights, put to `--level=0` alone: each stopped the replay, status 7. A changed bit is no lost mask, and neither audit has been shown a faulty public file of that size (docs/limits-all-rows.tsv, rows HW-747 and LIM-63.2);
   - at full size, the batch's audit with other bytes in the place of its kept file (at that size only the commitment's audit was tried in this way, but for one run, not on the released programs, as reported, in which a false file stood in turn for each of four kept files and the audit said no each time: docs/limits-all-rows.tsv, row LIM-63.2, line 5);

## Other ways to call it

`audit.py` (usage in its first lines; its first word, `<tree>`, must be the repository that this `audit.py` is in; the folder of `pubtool`'s output that it asks for is the one that the two scripts make in the work folder, `f<field>/pub.<16 digits for the configuration>.<16 digits of the sum over the sources>`) also audits proofs, if they were made under `-test-seed` and `-test-coins` and the programs' own lists of draws were kept (`COINS_CONTEXTS`): `--level=1`; written for one batch, first live copy 0, no empty slot and no failed request. In a proof the hiding sums of the sub-proofs' own rounds are not checked (35 a proof at the small sizes, 185 at full size).

`--level=0` needs no secret: it parses every byte, replays every chain, and checks that no masked number is zero or appears twice. `--drawn` is for files made without test options: only the stored tables' salts can then be checked, on synthetic weights, like every call that is given a secret folder. `--no-answers` tests the tool itself («What a YES does not cover», 9): it derives the keys without the records' answers, and every value that hangs on them must be reported. `--flip` tests the tool itself: it flips bits in its own copy of the files; every flipped value that a check covers must be reported, and nothing else. `--report=` and `--ledger=` write new files only; they are refused (status 2) where the file's folder does not exist, or another account may be able to change it or a place above it.

## What has been run

On the released programs both audits ran once at small size, on synthetic weights, with this repository's own audit files, on two commitments, each under a seed that `cp_commit` drew: they accepted the honest files, and `cp_verify` accepted the four proofs of the two kept batches; when a false file stood in turn for each of three kept files, under the tool's `--rehearsal` option, the audit said no each time; for a fourth kept file none was tried; no altered public file was put to them. Under a clipped-gap policy both also ran once, at small size (docs/limits-all-rows.tsv, row H13.8). At full size, in [the timed runs](../../docs/limits.md#the-timed-runs), the commitment's audit accepted three honest commitments to synthetic weights, under drawn seeds (no false or altered file was put to it; this is reported by the runs' own summaries: what the audit printed was not kept, and only its exit code, the form of its last line, how many lines report a failed check and how many kept files were left were looked at), and a fourth, made under a clipped-gap policy, of whose output the last six lines were kept (docs/limits-all-rows.tsv, row H13.7), and, outside the timed runs, `--level=0` over the public files and proofs of two commitments made by the released programs, one to synthetic weights and one to a real model's public weights, reported nothing and stopped at each of six copies with one bit changed (docs/limits-all-rows.tsv, rows LIM-63.2, line 1, and HW-747); for these two commitments the tool's files were this folder's, by their sum, this page apart. Every other run told here was not on the released programs, and on synthetic weights, mostly once. The runs told below were also made with other sources of this tool: from reading the code, the tool in this folder does not fit the files of some of these runs. The nearest of them was used in some of the audits at the default setting, and in no run on a planted fault or a lost draw: this folder's files differ from it, apart from this page, in three lines, in each of which a name differs, in one line of `cut.py`'s code, in the words of some comments and in two printed sentences. What this folder's own files have reported of lost draws: docs/limits-all-rows.tsv, row LIM-63.2, line 3. What the audit does not see, by a reading: row HW-626.

**The two audits at the default setting, under a drawn seed.** At full size, not on the released programs, both said yes (10.22 % of the bytes of key file and entry, and 7.66 % of those of two proofs, key file and entry, compared by value; of the two proofs alone 8.91 %; what an audit does not compare it parses, replays and holds to its roots), and the commitment's audit said no when 32 other bytes stood for the key's kept file, in rehearsal mode. A wrong kept file changes nearly every recomputed value at once (at full size 21 of the key file's 22 compared classes): such a NO shows that the comparison is switched on, not that one lost mask would be caught.

## The files

`audit_commitment.sh`, `audit_batch.sh`, `play.sh`: the three commands above. `audit.py`: the program. `batch.py`: a batch's two folders and its slots. `cut.py`: parses the files. `coins.py`: the random generator, written from `docs/format/COIN-KEYS.md`; its ChaCha20 block function is adapted from D. J. Bernstein's public-domain chacha-merged.c. `level1.py`, `level1_proof.py`, `folds.py`: the checks. `kept.py`: the kept files. `field.py`, `fieldlib.cpp`: arithmetic. `pubtool.cpp`: public parameters, through the verifier's own code. `coins_known.py`: a self-test of the random generator against known answers in the tree. `test_field.py`: a self-test of field 2's code against a second implementation, the format's own functions (`docs/format/format_rules.py`).
