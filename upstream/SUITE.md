# The test suite

This page lists the tests of this repository that anyone can run. Each test is one row of a table: what it needs, about how long it takes, the command that runs it and what its output must show. The page is also the input to `run_suite.py`, which reads only the tables.

No test uses a real model's weights; the tests that need weights use synthetic ones. A test that passes shows that the programs or routines it names gave the expected answers on synthetic inputs, or that a file or program that should be refused was refused. It shows nothing more about soundness or hiding.

The programs and every test program are built for one prime field, p = 2^64 − 2^32 + 1; a command may say `--field 2`, which names that field and changes nothing. Words such as key file, leaf file and commitment ID are defined in [the glossary](docs/glossary.md). The programs, their files and some tests' names say "record" for a table's OOD answers: see [the glossary's entry "Record"](docs/glossary.md#record). Some test sources are run by no row; the head of nearly every one says how to build and run it. `prover/tests/tail_gam_test.cu` builds from prover/ with `OUT=<a folder of your own> ./build.sh tail_gam_test`. Add `-fno-ipa-modref` to a head's g++ line that lacks it (verifier/README.md says why). Never leave such a build's output in `verifier/src`: without `-o`, g++ writes `a.out` there, and the verifier's source digest, which covers every file in that folder, changes; a later run of the row `build.serving` then counts a `cp_verify` built before the change as built from other sources, and refuses it.

## Run the tests

```sh
D=$(mktemp -d) && ./run_suite.py cpu "$D/work"    # the tests that need no GPU; the runner makes $D/work itself
D=$(mktemp -d) && ./run_suite.py gpu "$D/work"    # needs nvcc and one H100 80 GB
./run_suite.py all list-only --list    # prints the tests and runs nothing; no folder is made
```

In zsh, type the commands above without the words from `#` on, or run `setopt interactivecomments` first: by default, at its prompt zsh does not read `#` as the start of a comment, and takes those words as part of the command line.

If you run the tests as root, for example under `sudo`, first read the paragraphs below that begin «The sandbox is there» and «Under `sudo`»: they say what a test can then still do beyond your own files, and what changes for the files that the run makes.

- `cpu` runs the tests of the kind cpu, except any test that needs a row of the kind nvcc, gpu or gpu-by-run: the runner names each such test in a line that begins `left out`; `all` runs them.
- `gpu` runs the tests whose kind is nvcc, gpu or gpu-by-run, and the rows that they need.
- `long` alone runs the tests of the kind long: `integer_model.cpu` and `tools.lean_verify.full_size`.
- `--only <regular expression>` runs, among the tests of the kind asked for, those whose names the expression matches anywhere, together with the rows that they need.
- `--jobs <n>` sets the number of job slots: each test takes the number in its «slots» column, and one slot stands for one core and about 2 GiB of memory. The runner uses that figure only to choose how many tests run at once; it does not limit a test's memory.

`./run_suite.py --help-more` gives every option and rule.

What the tests need: Linux with Landlock in its kernel, `flock`, `make`, g++ 13 with its address and undefined-behaviour sanitizer libraries (libasan, libubsan), Python 3 and realpath; for the GPU rows also nvcc 13.2.86 (a later toolkit is not supported) and one H100 80 GB. Some rows need more, and count as not run, or pass in part, without it: pytest, numpy, gguf 0.19.0, clang++, util-linux's `prlimit`, and Lean with the library built (tools/lean-verify/README.md, "What to type"; lean/CHECKING.md, «Before you start»). scales/README.md, «Try it», gives the lines that make a Python environment with numpy and gguf, and integrations/README.md, «Tests», adds pytest; run the suite from the shell where that environment is active. On a system with nothing beyond what the install line in docs/quickstart.md installs, a run of mode `cpu` ends at best with status 77, not 0. Some tests use the CPU's SHA instructions (sha256rnds2): on a CPU that cannot run them, such a test ends with status 77 and a line that says so, and counts as not run; `weight_sums` fails there. `tools.confine` fails where /dev/shm exists but your account cannot make a file in it. Under the runner each row has a home folder of its own, so for `tools.lean_verify.full_size`, where `lake` is elan's, elan downloads the Lean toolchain again (some 540 MB, 2.8 GB on disk) or, without the network, the row fails; confined, a write of Lake's below lean/.lake also fails the row, and so does a run by another account than the one that built the library.

The work folder must not exist yet, must lie outside this folder, and its path may hold only letters, digits and / . _ -, with no part that begins with -; the folder above it must exist. If another account might be able to change a folder on the way to it, or to `BUILD`, nothing runs and the runner ends with status 2, because that account could put another folder in its place while tests run. A work folder below a fresh `mktemp -d` folder, in your home folder or directly in `/tmp` passes. If the message names a folder of yours, `chmod go-w` closes it. Where new folders come out group-writable (a default umask of 0002, as on a bare Ubuntu 24.04), run `umask 022` before you make the work folder, or `chmod go-w` those folders on its path that you have just made yourself. On a machine where you trust every account, such as a container of your own, `--i-trust-every-account-on-this-machine` lets the run go ahead past a folder that other accounts could change, but never past one that is missing or cannot be examined, and the first and last lines of the run say so. Even with that option, many tests fail on such a folder, because the scripts they start make the same check. Each test runs in a new folder inside the work folder. The programs and a few tests build into `bin/` and the GPU programs' build folder, `<work folder>/build` or the folder that `BUILD` names. The row `build.verifier` builds the verifier into the repository's own `bin/`, so a `cp_verify` that you built there yourself is replaced by one built from this folder's sources, if that build succeeds.

By default each test runs confined by `tools/confine.py`, which uses the Linux kernel's Landlock: it may write, make or remove files only in its own folder, the run's shared folder, `bin/`, and, for rows that build, the GPU programs' build folder, and besides them files in `/dev/shm`. A test of the kind gpu or gpu-by-run may also write the GPU's device files (`/dev/nvidia*`) and the files of `/proc`. The sandbox never confines a file's mode, owner or times: a test may change them on any file of your account. On Linux 6.12 or later a test may signal only its own processes; before Linux 6.12 only a signal to every process of the account is refused, and under root that leaves every other process of the machine in reach (a test that ends processes by name would end every matching process on the machine). The runner's first and last lines say which of the two holds. A row's command that you type yourself, without the runner, runs outside the sandbox. On a kernel without Landlock, or before Linux 6.12 on a machine that is not x86_64 or aarch64, nothing runs unless you give `--unconfined`, and then none of this is enforced. What the sandbox does not cover is listed at the head of `tools/confine.py`.

The sandbox is there to limit what a faulty test can damage by accident. It is not a barrier against a test written to do harm, and when the suite runs as root it cannot be one. Run as root, a test can still change the owner, mode or times of any file on the machine (`chmod`, `chown`, `touch`), which the sandbox does not limit at all, and it keeps root's other powers, such as the network and the machine itself. Under root each test gets a mount namespace of its own, in which `/proc/sys`, `/proc/sysrq-trigger`, `/proc/irq`, `/proc/bus` and `/proc/fs` are read-only against a plain open by mistake, not against a test of the kind gpu or gpu-by-run that means to write there (a root command with such a test's rights has been seen to make them writable again: the head of `tools/confine.py`), and `/dev/shm` is an empty folder of the test's own (seen at work as root on one kernel, Linux 6.18; no test on a GPU was run as root: docs/limits-all-rows.tsv, row R1.1). Where root may not make such a namespace at all (root without CAP_SYS_ADMIN, as in Docker's and Kubernetes' containers by default), the runner's first line says so: `/dev/shm` is shared, and a test can remove, overwrite or empty any account's files there; and where those places of `/proc` are writable, a run that includes a test on the GPU stops before it starts anything, unless you give `--unconfined`. Where the namespace can be made but a later step fails, nothing runs as root; `--unconfined` runs the tests without the sandbox, on purpose.

Under `sudo` the runner runs as root, so what it makes belongs to root: the work folder with everything in it and, if this folder had no `bin/` before, `bin/` with the programs built there. Your own account cannot remove that work folder, or write in a `bin/` that root made: in a later run without `sudo`, the tests that build into `bin/` fail, and every test that needs one of them is not run. That this `bin/` is root's does not protect it: whoever owns the copy can replace it, `cp_verify` included. Under `sudo` these tests act as root on names inside the copy, so whoever owns the copy can steer what root does there, as with any program run by `sudo` from someone's copy. To go on without root, start again in a new copy of the repository.

None of the tests' calls removes, moves, overwrites, empties, or changes the mode or owner of a file outside the work folder, the repository's `bin/` and, for rows that build, the build folder that the runner names in its first line, except files and folders of their own in /dev/shm, with names that begin `confine-test-`, `run-suite-test-` or `.check-`, which `tools.confine`, `sources.run_suite` and, through `integrations/proof_middleware.py`, `integrations.unit` and `integrations.cp_verify` make and remove. This rests on a reading of the calls written in the repository's files that the tests run; `tests/dangerous_calls_test.py` checks the recursive deletions and the signals among them against `tests/dangerous_calls.tsv`, but not single removals, renames or emptying. It does not cover appends, changes of a file's times, or what outside programs that a test starts (such as nvcc, g++ or pip) do.

A test that runs past its time limit (five times its «minutes», and at least ten minutes, or at least an hour for a test on the GPU when `GPU_PREFIX` or `GPU_LOCK` is set) gets SIGTERM for every process still in its process group, and SIGKILL for any that are left twenty seconds later. A test of the kind gpu or gpu-by-run gets no signal at all, because killing a program while its GPU code runs can take the whole machine out of use: the runner names it in capitals, leaves it running, counts the test as failed, starts no further test on the GPU and finishes the others. Only a test of the kind gpu that is still waiting for the card's lock is ended as other tests are.

Each table has eight columns. «kind» is cpu (no GPU), nvcc (needs the CUDA compiler but no GPU), gpu, gpu-by-run (a test that holds the GPU only around each GPU program it starts), or long. «needs» lists the rows that must pass first. «word» is any on every row of this page. «slots» is how many job slots the row takes. «minutes» is a rough estimate of how long the row takes on one machine; it sets the order and the time limit. «passes» lists the exit statuses that count as a pass; after a space may follow a regular expression that the last line of output must match, and after each ` ;; ` another one that some line of the output must match. «command» is run by bash from this folder, with `T` set to this folder, `W` to the test's own folder (not made yet), `S` to the run's shared folder, `B` to the GPU programs' build folder and `WORD` to the version word.

The runner's own exit status:

- 3: a test ended with status 3, whatever else happened.
- 1: otherwise, a test failed, a test was not run for a reason of the run's own (a test that it needs failed or was not run for such a reason, a GPU program that an earlier test had left running still held the card, or the work folder was replaced or removed before it could start), a line was printed after the word `LOOK`, the work folder was replaced or removed during the run, or the runner itself got SIGTERM, SIGINT, SIGQUIT or SIGHUP.
- 77: otherwise, the only tests that did not pass were not run and said why in their last lines, together with tests that could not run only because of those.
- 0: otherwise.
- 2: nothing ran: the call is wrong, no test is to run, the work folder or `BUILD` lies below a folder that another account might change, or the tests are to be confined and the work folder lies on `/dev/shm`'s file system.

`--list` ends with 0. A test that would otherwise pass but whose last line begins with `not run` could not run on this machine, and counts as not run. A test that ends with status 77 where its row allows it, and whose last line does not begin with `not run`, ran only in part: it does not stop the status from being 0, and the runner's last line counts such tests, so read it.

Some test programs run through `prover/tests/unit.sh`, which writes the program's own lines to `<program>.log` in the folder that the row's command names. For those rows the runner sees only unit.sh's status and its few lines: a program's status 3 reaches the runner as 1, so read that log when such a row fails.

Some tests run a prover that argues for something false, made so by the test's own code, or inject faults into test programs, all on synthetic data, so that you can watch a check refuse the false proof or claim. Use nothing from the work folder for anything but these tests. The prover's sources also call test hooks, each inside three lines under TEST_HOOKS; the hooks' code is not part of this repository, so no build with that switch can be made from it.

## What a test's exit status means

- 0: everything ended as the test expected.
- 1: something did not.
- 2: a wrong call.
- 3: `cp_verify` accepted a file or a statement that it should have refused, and the test did not expect that; or, in `verifier.ws_build_fuzz`, the verifier's layout routine gave a layout outside its bounds; or another program in that test ended with status 3, so read the test's output to tell which. Keep as they are the work folder, `bin/` and the folder that `BUILD` named, if it was set; and report it: SECURITY.md in the top folder says how.
- 77: the test, or a part of it, cannot be run on this machine.

Most tests that end with status 3 also print a line with the words `WAS NOT REFUSED` and keep what was accepted. That every test does so has not been checked. These do otherwise. `verifier/tests/served_form_test.py` ends with 3 without the words; it and `what_a_yes_covers_test.py` say only that a call ended "not as expected", so such a row is reported as `ACCEPT` without a line after `LOOK`. `tests/new/run_new.py` and `examples/rejected-proofs/try_altered_copies.py` have words of their own (ACCEPTED; WAS ACCEPTED). `verifier/tests/clang_build_test.sh` counts the status 3 of `made_up_files_test.py` as a failure of its own: it shows the line with the words and ends with status 1. Other tests tell an accept only as a failed expectation in words of their own, among them `blocks/first_look.sh`. Tests of many cases remove the files of the cases that were refused; the accepted ones stay. Not known: whether each test compares the last line on an expected accept; the tests have not been read one by one for that.

`run_suite.py` prints the lines that its own list of wordings matches after the word `LOOK`, whatever the row's status. The list is not complete, so a row that failed without a line after `LOOK` can still be such a find: read its output, which the runner keeps in `screens/<test>.txt` in the work folder (for a test that runs through `prover/tests/unit.sh`, also the program's own log). Some of these lines are also printed where a test failed for another reason. The runner searches only what a row's command prints: `prover/tests/unit.sh` and `prover/tests/psc_rows.sh` print only lines of their own, so a find in a test that runs through one of the two shows as a plain failure.

These rows run what docs/quickstart.md offers a first-time user: the two blocks of commands in its section 3 that build and run the example, not the block that checks the machine, and the example script `prover/examples/run_target_example.sh` on one GPU, and `blocks/first_look.sh`, which makes and checks toy proofs on a CPU alone.

## Refusals of altered, malformed and extreme files

These rows give altered, malformed, cut, crossed or extreme files, parameter files or calls to `cp_verify` itself in most rows, directly or through a script that runs the programs; in the others to the committer or the prover, to single routines of the verifier in a test program, to the tool `prover/tools/pack_layout.py` (`tools.pack_layout.refusals`), or to the library's example programs with a second verifier in Python (`examples.protocol_toy_false_files`): each row's command says which. Most check that each is refused; a few check only that the program ends cleanly, with a plan, a named refusal or a usage message and no crash. The common names of the verifier's refusals are explained in verifier/docs/output.md, section "Rejection names", and every name in docs/format/FORMAT.md, section 13.8.

No row on this page gives `cp_verify` a proof made by a cheating program. No one list gives, for each kind of false input, the test that tries it and what is left untried. No row on this page tests any of the six things that follow, nor these two: that a partial check, or a full check on honest files, names the condition of the standard parameter form that is not met, apart from `next-token` and `id-named` in a full check and `no-proof-of-work` in a full check and in both partial checks; a proof made with counted proof of work under a changed setting (docs/limits-all-rows.tsv, row E11). Many tests' files say in their head comment what the test leaves untried.

- The last-round check that the word the prover sent, re-encoded, matches the symbols opened at the drawn positions. No run has shown this check to be the one that refused a false proof.
- That a commitment to a word far from the code is refused, which is what the proximity test is for: the committer here always commits to a codeword, so no test can commit to a word that is none.
- The check that a request's first chain and the shared chain use one set of codes, one shape and one table; without it a claim on another matrix was accepted in a test program.
- That the verifier's lookup routines accept a lawful count at a repeated table row.
- That a prover who retries its nonces against a word mixed from two codewords does no better than the design predicts.
- The verifier's claim-by-claim approximate range check, which has its own test in the tree (verifier/tests/tail_twin_test.cpp) that a reader builds by hand.

`verifier.call_accounting.examples` runs on honest proofs alone. It does not show that an altered or forged proof cannot make the verifier hash more than it planned, and no other row tries it.

## The proof library's own tests

The proof library in `blocks/` is what the three programs are built on. Its own unit tests run on the CPU, at toy sizes, on synthetic data, and call the library directly; inside a request's sub-proofs `cp_prove` and `cp_verify` run implementations of their own of the masked sum-check, the look-ups and the range check, about which these tests say nothing (prover/README.md; docs/limits-all-rows.tsv, row SO-12).

`second_writings.honest` gives toy files to the library's C++ verifiers and to second verifiers in Python. It changes the first OOD answer in a toy key file and in a toy leaf file. Both altered files are refused at a proof of work, because the answers are hashed at the start of the file's hash chain, so this test never puts a false answer before the equations that tie the OOD answers to the table (Parts 9 and 10 of docs/format/toys/3-key-and-entry.md: the equations (Rec_i) and the record's rows). On synthetic data, in a run of the project's own, the second verifier of key files refused a false key file that is not part of this repository, so that a reader cannot repeat it, at the one batched linear check that holds these equations and those on the opened columns. By a reading of that verifier's code and of the outcome, its false pad had made one of these equations false, together with those on the opened columns. Such a check cannot say which equation decided, so that file does not show these equations refusing by themselves.
