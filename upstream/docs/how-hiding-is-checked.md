# How weight hiding is checked

This page tells what was run to check weight hiding: what each test and audit looks for, what it cannot see, and which of them you can run. Masking is built in and on by default. What is claimed, and what is left, is on [guide/weight-hiding.md](../guide/weight-hiding.md).

<a id="faults"></a>
## Faults: who stops them

A main risk is a lost [mask](glossary.md#mask), silently dropped by a bug or a hardware fault: a file with an unmasked value can still verify, and no verifier can see it.

- **Self-checks.** A [self-check](glossary.md#self-check) is a check that `cp_commit` or `cp_prove` runs on its own work in every run. Some compare a secret random value with a second derivation of it; by a reading of the code, most other random values in CPU memory are compared with nothing after their sampling. Which self-checks have been seen to fire at the default setting: tests 2 to 4 in the table on this page. No run at the default setting is known in which the read-back check, which looks for a mask that was never written, fired (row HW-457 of [the table](limits-all-rows.tsv)).
- **The verifier.** `cp_prove` runs none: it releases a batch's responses once all of them are staged, so a file spoiled by a bug or a hardware fault leaves the prover, unless a self-check stops the run. A file that does not verify can lack a mask, and a client whose own verifier rejects it already holds it. So no response may leave the provider before `cp_verify` has accepted every proof of its batch ([duty 6](limits.md#the-conditions)). That holds of every file of a response, its token file too: nothing leaves that `cp_verify` was not given. The vLLM integration that ships hands on no proof, and nothing of its response, before `cp_verify` has passed every proof of its batch (narrow exceptions, none open to a client: [integrations/LIMITS.md](../integrations/LIMITS.md#narrow-exceptions)); `driver/measure_rate.py` reports no rate, and an example script shows no answer, before `cp_verify` has accepted the proofs; and a front end of your own must do the like. A verifier rejects only what does not verify, so it misses a lost mask where the file still verifies, yet for many faults it is the only check.
- **The audit with the key**, in two tools that a provider starts, recomputes part of the published bytes from the provider's secrets and compares them. It compares no value that depends on the weights, and it takes commitments to synthetic weights alone.

No program detects a use counter set back by restoring or copying the secret key directory: that is the provider's duty. What the batches past the limit give away (by reasoning: row H21.11) has not been tried on the released programs. By a reading of the code there are kinds of fault that no check would catch, and the list of them is not complete (rows HW-695, HW-756; what looks for a fault, kind by kind: rows HW-684 to HW-693, HW-321, HW-322 and HW-326).

## What tests of hiding exist

Every test of hiding used [exact match](glossary.md#exact-match); none used a score policy such as [clipped gap](glossary.md#clipped-gap), audits apart (rows H13.7 and H13.8).

**How much was tested.** At the [default setting](glossary.md#default-setting): five tests, nearly all at small size and on synthetic weights, two of them on the released programs; a few audits; one short search of honest public files for leaks; one count of derived random values over two small commitments; and one fast reading of the sources of `cp_commit` and `cp_prove`, in a text from which these sources differ; nothing else. Three proofs made at the default setting have been searched for a leak, at small size, not on the released programs, and in part only: of each proof the search studied by value the opened columns of the stored tables and their salts; every other field it looked at only as bytes, with a net for gross faults; it found nothing, which is worth little (row LIM-29). No other proof has been searched.

**Five tests,** at the default setting, on synthetic weights and at small size, a small test shape, unless this page says otherwise. Some ran more than once: a repeat of a test is no new witness (row LIM-63.2). None of the five searches for a leak: they test that the masks are there and that a loss is noticed. The outcomes are reported: told from the runs' own accounts and logs, not from a second, separate run. That the programs were the ones named below rests on the runs' records.

| Test | What it looks for | Outcome | Biggest blind spot |
|---|---|---|---|
| 1. The OOD answers, by value | Whether each published out-of-domain (OOD) answer, a masked sum of the weights, carries its own [pad](glossary.md#pad) | Every answer checked carried its pad: 1,536 at small size, 4,096 at full size | That the pads are random it does not show, nor what an answer gives away |
| 2. Lost pads | Whether injected losses of pads stop `cp_commit` before a public file exists | All 8 losses stopped `cp_commit`, on a test build of other sources (defined below) with all weights 0; none left a public file, and no loss was of a single pad (row LIM-26.1) | By a reading of the code one self-check is all that stands between a fault that loses every pad and a public file without pads; with it switched off, on a test build (without [proof of work](glossary.md#proof-of-work), which the default setting counts), a commitment without pads passed everything else that `cp_commit` does (one trial) |
| 3. The sweep of lost random values | Whether anything stops the programs when a random value is overwritten right after it is drawn | GPU memory: 130 of 130 stopped, 122 of them by one self-check alone. CPU memory: 123 of 165 stopped, 30 unnoticed, 12 changed no file (picked cases, so no rate) | What an unnoticed loss exposes it does not show; its 295 runs, one loss each, struck 189 different draws of 73,177; it did not run at full size, with two losses at once, or with a loss later than right after the draw; its runs are one fixed sample, no second witness (row HW-660) |
| 4. The replay of riskier losses outside that sweep | Whether losses at draws that a self-check covers are stopped | 263 of 263 stopped; 9 of 9 at draws that no self-check covers unnoticed | Far more draws that no self-check covers exist; nothing ran at full size (row LIM-63.2) |
| 5. Both audits with the provider's secrets | Whether the audit tools accept honest files | Honest files accepted at small size. At full size the two tools ran together only on other programs; one of the two, the audit of a commitment, also ran on the released programs, on none but honest commitments, and accepted them, in [the timed runs](limits.md#the-timed-runs) | They compare only part of the bytes by value (7.66 % to 33.00 %, by audit, size and policy; the least of these at full size, in a run not on the released programs: row LIM-63.2, line 5); whether a mask was applied to the value that it should hide they do not ask |

The second and the third ran on test builds of other sources, which hold the code that injects a fault, and the fourth on programs of other sources that held test-only code. The released programs are `cp_commit`, `cp_prove` and `cp_verify` as the sources in this repository build them (the production build). *Other programs* (test builds and test programs among them) are programs that are not the released programs: [which those are](limits.md#what-was-run-on-these-programs), and [what these pages tell of the others](limits.md#on-other-programs). What a run found on them does not carry over to the released programs; what a reading found carries over only as far as the differences up to the released code were read (row HW-679). A fault found on them may be in the released programs too. Not every test build in these pages was made from these sources. Where a run on a test build is told, no public test of SUITE.md is named and the sources are not said, count what it found in favour as found on other sources; a fault that it found may be in the released programs too. *These sources* are the sources in this repository. What ran on the released programs, from which sources the programs that ran were built, and what ran on other programs: [docs/limits.md](limits.md#what-was-run-on-these-programs).

**Injected faults.** An injected fault is one put into a copy of the programs on purpose; in the other tests memory was overwritten in a running program. A fault went unnoticed if the file verified and nothing stopped it; it was stopped if a self-check did; none told here gave a file that did not verify. No way for a client to cause an injected fault is known, but none has been looked for. No fault has been injected into the released programs, which have no option for it, and no broken duty has been tried on them, unless a row says so: what a page or a row says of a fault or a broken duty is read or reasoned, unless it says that a run was made. Outside a trial a code review found one fault that nobody had injected, a mask never generated, in a routine that no program called; whether the released programs hold that routine or call it is not known (row HW-753). Little would show another such fault. Two bad results stand apart. One is of a 16-bit weight file that somebody else can write: row H46.4. The other: the number of events in a reply streamed by vLLM differed between runs that differed only in hidden values, and it is not shown that hidden values leave that number unchanged ([integrations/LIMITS.md](../integrations/LIMITS.md)).

**Searches for leaks.** One short search has looked for a leak, in the public side of two small honest sets, not on the released programs. It found nothing, which is worth little: on the first of these sets the search's first look cannot see any fault of a pad at all (as reported: row LIM-29). Such a search finds no leak that comes from the protocol's rule itself. Three proofs made at the default setting have been searched for a leak, at small size, not on the released programs, and in part only: of each proof the search studied by value the opened columns of the stored tables and their salts; every other field it looked at only as bytes, with a net for gross faults. No other proof has been searched. No file at full size has been searched for a leak, no test has searched two commitments to the same weights together, and none has been aimed at batches that overlap in time, which is how the service works by default. (No search for a leak: in four full-size proofs under one commitment at a time the audit tool's program looked only for a masked value that is 0 or stands twice: row HW-747.) A provider proves whole replies, and how a wider request affects hiding is not known. A count over two small commitments to one set of weights found no derived random value twice, not on the released programs: a net for gross faults, no more, which shows the schedule of keys, not that the programs used these values (row LIM-63.2, line 12). More that has not been tried: the rows under the heading that begins "not tried" in the index at the head of [the table](limits-all-rows.tsv).

**A reading of the code.** 384 files of a text from which these sources differ were read once and fast, for hiding alone: all that a production build of `cp_commit` and `cp_prove` from that text reads, but for `cp_verify`'s own 36 files, on which every rejection of a false file hangs. The reading found no leak beyond the [declared list](what-is-not-hidden.md), in a correct build and with the provider's duties kept. That means that none was found, not that there is none. The reading does not settle nine points, and is not certain of a few more (listed in row HW-745). Nothing was built or run, nothing compiled was seen, and the arithmetic was not checked. It asked whether a value leaves without its cover, not whether the covers suffice, and weighed one fault at a time. For many single faults the one net that the reading found is a verifier's run on the response before anyone else holds it. `cp_prove` makes no such run: that net lies with the vLLM integration that ships, or with a front end of the provider's own, and the reading did not read the front end or the other scripts ([duty 6](limits.md#the-conditions); row HW-745). 188 of the files were read twice, on one brief, so two readings of a file are not independent. Some of its reasons rest on comments, not on code. In all, these sources differ in code in 68 of the 384 files, and in 136 more in comments, names and the wording of messages alone; two more of the 384 are not among these sources; in the 68 the differences in code were read for hiding, by difference alone, apart from renamed names and reworded messages, and the files were not read whole again (row HW-745). One of the 68 holds the class that feeds and finishes BLAKE2b, which the reading saw in another form (row HW-748).

**Which tests ran on a production build.** A *production build* is what the build script makes unless a test build is asked for, and it accepts no test options. A *test build* has them, such as a fixed test seed. Only a few checks of a proof's masks by value ran on a production build; the others ran on test builds, which are assumed to apply masks in the same way. Two of the five tests have run on the released programs: the first at small size on synthetic weights and at full size, once on synthetic and once on a real model's public weights, and the fifth, which is both audits, once, at small size on synthetic weights, under exact match; both audits also ran once under a clipped-gap policy (row H13.8). One of the fifth's two audits, the audit of a commitment, also ran on them at full size, in the timed runs (row LIM-63.2, line 5). At full size the first test has also run on other programs, and the fifth's two audits have run together only on other programs. In a production build no self-check has been seen to fire for a lost random value: it has no way to inject one.

## Run a test yourself

Of the five tests on this page, the fifth is in this repository: the two audit tools under `tools/audit/`, with their own test. So are the public tests named below. By two readings of this repository's files, it does not hold the programs and scripts of the first four tests, of the few audits beside the five, of the one short search for leaks (row LIM-29) or of the count of derived random values: a reader cannot repeat these from this repository. `cp_commit`'s range check is a check inside the program, and hiding was not tested with it. With one H100, run the audit's demo: "Try it" on [tools/audit/README.md](../tools/audit/README.md). It tests the tool, not whether the programs hide the weights.

Without a GPU, these rows of [SUITE.md](../SUITE.md) come nearest to hiding. None of them tests the GPU code or a full-size model, or runs `cp_commit`, `cp_prove` or `cp_verify`. Run them from the top directory of the repository; SUITE.md gives `blocks.tests` 13 minutes, and one of its programs takes 5.4 GB of memory:

```sh
D=$(mktemp -d) && ./run_suite.py cpu "$D/work" --only '^(blocks\.tests|prover\.guards_stand|prover\.masking_cells_test|toy\.mask_rules|verifier\.hiding_coins|tools\.audit\.coins)$'
```

A passing run shows that these tests gave the expected answers, not that the weights are hidden.
