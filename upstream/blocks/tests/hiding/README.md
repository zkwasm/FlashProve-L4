# blocks/tests/hiding/: tests of hiding

A soundness fault shows when a verifier accepts something false. A hiding fault shows nowhere: every equation still holds and every proof is accepted, but the proof reveals something about the witness. So these tests examine the prover: how what it sends depends on its coins, what is in its memory, and the run-time guards with which it stops itself.

Words that the tests use and print. The prover's *coins* are its private randomness; in the exact test they are the field elements that it draws. Its *view* is every field element that it sends or opens; digests and salts are not in the view. The *law* of the view is its distribution under uniform coins. A coin is *curved* if it occurs in a product of coins, so that the view is not affine in it. The programs print *planted* for a faulty layout that a test was written for, *control* for a fault that a test injects for itself, and *keeper* for the holder of a committed table (here `IndexCpu`, on the CPU). Other terms: [docs/glossary.md](../../../docs/glossary.md).

| file | what |
|---|---|
| `exact.h` | The exact test. With the verifier's messages fixed, it runs the honest prover once for each of its coins. Then it asks, by linear algebra over F: are there coins under which a second witness gives the first witness's view, and do the coins change both views in the same directions? The comment at the top of the file says what the test detects and what it does not. |
| `exact_self_test.cpp` | Runs the exact test on provers of a few lines whose laws are known. The test must not pass where the laws differ or where nothing was tested, and it must not fail where they are equal. |
| `psc_exact_test.cpp` | The exact test on one block, the zero-knowledge sumcheck, in the large field. It has 22 negative controls, of two kinds: a fault in the mask row, and the value 0 for the challenge that multiplies the inner masks. |
| `toy_exact_test.cpp` | The exact test on whole proofs: `toy/product.h` and `toy/segments.h`, at a size small enough to read by eye. The coins are all field elements that the prover draws. The view is all field elements of the proof. |
| `guards_test.cpp` | Shows what the run-time guards of `iop/context.h` are for. It has six faulty layouts, made for this test. In this repository it runs each one's valid counterpart; a build of it that is not part of this repository runs the faulty ones. The guards stop each of them, four of them on the verifier's side as well. With the guards switched off, the verifier accepts (it prints "says yes") and the exact test tells two witnesses apart. |
| `lkp_exact_test.cpp`, `rng_exact_test.cpp`, `wf_exact_test.cpp` | The exact test on the look-up alone, on the range check alone, and on the proof of a table's ranges alone. The fixtures are `iop/tests/lkp_world.h`, `rng_world.h` and `wf_small_world.h`: small cases that stop after the block, so the view is sample answers and scalars, and nothing is opened. With the argument `long`, the look-up and the range check also run whole, with a proximity test of two stages after the block. The range check also runs in the protocol's reference shape. There a group has one mask row, in its first message, so two sampled messages (the digits, the multiplicities) have none, and the pads of their samples are in main rows. In that shape the sending block draws every pad, and the test passes only if the two laws are the same. |
| `table_exact_test.cpp` | The budget of a committed table, tested on the table's holder alone (printed: keeper). The test's own fixture sets up these misuses: one batch more than the count allows (the caller does not ask the holder); a table made again from the same coins; two tables with the same random entries; a second record on the same pads; two tables with the same pads. Each of the five runs in `make test` as a negative control: the program fails unless the two witnesses are told apart at a named entry of the view. Nothing in the library is changed for them: the fixture leaves the holder's count unasked, gives two tables the same random tails or the same pads, or computes a second record itself. No verifier runs in this test; by the comment at the top of the file none can detect the first three. |
| `sessions.h`, `lin_exact_test.cpp`, `member_exact_test.cpp` | The exact test on whole sessions on a committed table (`iop/tests/lin_world.h`, `member_world.h`). A session is the committer's run and then a batch of requests, on three kinds of hash chains (one that the batch shares, and a first and a second chain for each request). The witness is the table's matrix. The view is what all requests of a batch see together. `lin_exact_test` and `member_exact_test` each have a negative control in which a table's rows' pads are zeros, and `member_exact_test` a second, in which the last entries of Omega's random tail are zeros, as many as the lists of all requests but the first have positions. At each two matrices must be told apart. |
| `link_exact_test.cpp` | The exact test on a whole LINK proof (`iop/link.h`), with both committers' runs before it. The witness is the rows that both tables hold. The view also has both tables' records. Three negative controls change the coins: in one the copy is made with the first table's random tails, in another the copy's tails are constant, in the third both tables' pads are zeros. |
| `key_exact_test.cpp` | The exact test on a whole key file (`frame/check_key.h`), at the smallest whole case (`iop/tests/wf_small_world.h`). The witness is the table's matrix. By the head of the file the test takes about nine minutes and 5.4 GB with four processes, so it runs only with the argument `long`, which `../../Makefile` passes. Without the argument the program prints that it was NOT RUN and ends with status 77. With `two-mask-rows` beside `long` it runs a second case, in which the index-mask message has two mask rows and the message on the ranges has nine (by the same head, four minutes and 2.5 GB). `make` does not run that case. With `pads-are-zeros` beside `long` it runs one negative control, in which the table's pads are zeros and the two matrices must be told apart; `make` does not run that case, so no run of `make` shows this program fail. It asks one thing more of the honest run: by the test's linear system, with no further run, the two matrices would be told apart if the table's random tails or any row's pads were constants. |
| `salts_test.cpp` | Checks that every leaf has a salt made from its own bytes of the coins. (The exact test leaves salts and digests out.) |
| `hull.cpp` (with `iop/message_dump.h`) | The sampled hull, for a prover whose coins cannot be set one by one and whose files are long (the GPU programs). It takes many runs under fixed challenges and applies linear algebra to sets of sent entries. It is weaker than the exact test: the comment at the top of the file says what a pass does not show. Without arguments it tests itself on the two toy proofs and on two made-up provers, one of which has a fault that it must find, and checks that `message_dump()` ends the process, and leaves what is there as it is, where a file or a symbolic link already has one of its two names, in three such cases (the comment at `standing_names()` says which, and which are not shown). |

## Three switches for tests

- `BLK_TEST_PROVER_MESSAGES_OUTSIDE` (`chain/rounds.h`): nothing that the prover sends enters its queries to the hash chain, so its challenges do not change. No verifier is changed, and none accepts such a proof. If `first_query_stands_still` is set as well, the chain also starts from zeros. That is for a prover whose statement depends on its coins.
- A switch that is not part of this repository, for builds of tests that are not part of it either: a `BLK_REQUIRE` whose message the test has listed does not end the process, whether it is in the prover's code or in the verifier's. No `BLK_REQUIRE` depends on the bytes of a proof, so no check of bytes is changed. But the rules on what may share a leaf are in the verifier's program too, because a layout is public. So a verifier that "says yes" to a faulty layout is one whose own guards are switched off. That build of `guards_test.cpp` runs the verifier both ways: with all guards switched off, and with its own guards on.
- `BLK_LISTED_COINS_FOR_A_TEST` (`coins/tests/listed_coins.h`): coins that a test sets entry by entry.

A test file defines the other two switches itself, before its first include. No program that makes or checks a proof for anybody defines any of them. One test build of cp_commit, which this repository's build script does not make, defines the first, for a test of hiding.

## What these tests do not show

- **Toy sizes, and only the cases that were run.** All sizes are toy sizes. A pass covers only the pairs of witnesses and the lists of challenges that were run. The pairs are random, so a leak that shows only for special witnesses (zeros, one bit) can pass (see the comment at the top of `exact.h`).
- **Outside the method.** The tests show nothing about digests beyond the freshness of the salts, about coins that are not uniform (`coins/tests/`), about running time, or about a prover that stops or starts again for a reason that depends on the witness.
- **The exact test does not see a missing pad where other random entries hide the answer.** A pad is the random element that masks the answer to a message's out-of-domain sample (`iop/send.h`). Where other random entries of the message enter that answer and nothing else uses them up, they hide it as the pad would, and the exact test and the sampled hull pass a prover that draws no pad at all. A missing pad tells two witnesses apart only where the pad is the one random entry left in the answer.

  The test builds that show this, on a copy of the library in which `send_prove()` draws no pad, at toy size, on made-up data, do not ship, so it cannot be repeated from this repository. Each such build passes only if `toy_exact_test` and `hull` tell the two witnesses apart on `toy/segments.h` and not on `toy/product.h`, where the two witnesses have the same law. So a pass on `toy/product.h`, in either program, does not show that a pad is drawn; nor does a pass of `rng_exact_test` in the shape in which every message has a mask row.

  Whether pads are drawn is looked at elsewhere. `send_prove()` reads every pad back after the sending and ends the process if one does not stand at its place as it was drawn. `iop/tests/send_pad_test.cpp` reads the pads in the prover's memory, for the sending block alone, on eight lists of message shapes of its own. Eleven more tests under `iop/tests/` and `frame/tests/` compare the pads of two runs of their own blocks in the same way (`pads_fault()`, `iop/send.h`). No run in this repository shows that `pads_fault()` reports a pad that is missing or used twice.
- **Only the CPU reference runs.** Every prover here is the CPU reference (`EngineCpu`, `IndexCpu`, `HeavyCpu`, `WfCpu`, the look-up's CPU sums). No GPU engine and no GPU holder of a table runs, and none of the draws of private randomness that the serving programs make.
- **The record and the challenges.** A table's record belongs to the view of every test on a table. The tests keep it out of the chains' first queries, so that the challenges stay fixed: in `lin_exact_test.cpp` and `member_exact_test.cpp` a made-up record stands in its place, so each request keeps challenges of its own; in `link_exact_test.cpp` and `key_exact_test.cpp`, where one request runs, the switch `first_query_stands_still` puts zeros there. So what a pass says is said of the interactive protocol under fixed challenges, as for the prover's messages.
- **Random tails.** In the sessions, the table's random tails and those of the three fresh vectors (the folded row, W, the vector at the shared point) have no entries to spare: each is opened at as many lists of positions as its tail was sized for (see the comment at the top of `lin_exact_test.cpp`).
- **Openings.** The default runs of `lkp`, `rng` and `wf` stop after the block and open nothing.
- **What `make test` runs, and which tests can be seen to fail.** It runs each program as it is. A negative control is a fault that a program injects for itself, into its own random values or fixture, and must then see; the table above says which program has some. `toy_exact_test`, `rng_exact_test`, `lkp_exact_test`, `wf_exact_test`, `guards_test` and `salts_test` inject none, `key_exact_test` injects one only under an argument that `make test` does not pass, and `hull` injects one into a made-up prover and none in the two toy proofs: no run in this repository shows that these fail on a faulty form of the library's own prover. (`member_exact_test` and `key_exact_test`, like `lin_exact_test` and `link_exact_test`, fail unless, by the linear system of an honest run and with no further run, the witnesses would be told apart if a table's random tails or any row's pads were constants.) A fault that has to be built into the library itself (a sending block that draws no pad, or one pad for all places; one random value for two coefficients of a fold's hiding polynomial; salts that are shared or zero) is not in this repository, nor are the lists and tests that build it. Nor is the engine of a test build that sends a kept row again under the random tail of its first sending: the verifier accepts that proof, and the build passes only if the two witnesses are told apart in the run on `toy/segments.h`. Each program runs without arguments: one case and one or two pairs each, as its printed line says. Only `key_exact_test` gets the argument `long`, since it tests nothing without it. The other programs' further cases, pairs and special witnesses run with the argument `long`: `make long` (six programs; no row of SUITE.md runs it).
- **Curved coins.** Where the view is curved in some coins (the inner masks of a product), the test requires the triangular shape under which one list of coins, which it finds and then runs, is enough. The argument is in the comment at the top of `exact.h`.
