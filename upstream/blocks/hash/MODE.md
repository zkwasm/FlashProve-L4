# The hash of blocks/: BLAKE2b as specified, on labelled strings

This page is for a reader who checks soundness and hiding. **The rule itself, to the byte, is in docs/format/FORMAT.md, rules R2, R3, R5 and R7 (its sections 3, 4 and 6); where that page and this one differ, that page decides.** This page says what is assumed and on what grounds, what each kind of hash costs, why leaf, salt and round are laid out as they are, and what it does not decide. It claims no theorem. Terms: [docs/glossary.md](../../docs/glossary.md).

Public sources. [SPEC] Aumasson, Neves, Wilcox-O'Hearn, Winnerlein, "BLAKE2: simpler, smaller, fast as MD5" (https://www.blake2.net/blake2.pdf), section 2.8. [RFC] RFC 7693 (the compression function F; it prints only the first four bytes of the parameter block). [LMN] Luykx, Mennink, Neves, "Security Analysis of BLAKE2's Modes of Operation", IACR ToSC 2016(1), ePrint 2016/827.

## 1. The rule in short

    H(number, tree, index, start; bytes) = BLAKE2b( [8 bytes: number + 2^16 tree] [8 bytes: index] [bytes] ),   salt = start's bytes 0 to 15, personalization = its bytes 16 to 31,
    (of a leaf the first word also holds its shape: + 2^32 x the number W of its symbols + 2^56 x its salt's length in words of 8 bytes; of a round's call the chain's label stands in the tree's place)

The mode is sequential, with no key. The digest length is 32 bytes, and 64 for a call of a chain's round. A hash without a start is BLAKE2b without salt and personalization. Salt and personalization are used as [SPEC] means them, and nearly every library takes them (Python's hashlib; libsodium's crypto_generichash_blake2b_salt_personal; RustCrypto's blake2). BLAKE2b's field "salt" has nothing to do with a leaf's salt, which is part of the hashed bytes.

Whether a hash has a start depends on its number alone. All leaves of one tree start from one digest: the run's value or, for a tree that no run has made (a stored table, the tree that binds a batch's requests), the configuration's digest. The calls of a round start from the chain's value before the round. So a digest of the public parameters is in every hash of a tree and in every call of a chain.

**A vertex** is H(166, 0, 0, start = the configuration's digest; left digest, right digest). It holds nothing of the tree, the place or the run, and it is the same for every tree under one configuration (in the tree that binds a batch's requests the number is 178 in the place of 166). No statement about the protocol uses more. The verifier hashes every opened leaf itself, with its own start, tree number and position, which follow from its own plan and run, never from the file (FORMAT.md, R7.10, which names one exception: a request's slot in the binding tree, R7.18). Left and right come from the position's bits. The depth, and the number and order of the digests in an opening, come from the plan. Leaf and vertex differ by their numbers. With the leaves bound in this way, a subtree that is moved or borrowed opens nowhere: **the binding of the leaves carries all of it.** This holds for perfect binary trees only. The vertices do not narrow what one collision, once found, would reach; for trees made in a run, the leaves narrow it. This narrows how much cheaper further forgeries get after one hash collision and doesn't end it.

## 2. What is assumed

**One** oracle on byte strings, with 256-bit answers. The strings are those of FORMAT.md's R2.4 (a byte for the half, the parameter block, the label, the bytes). A 64-byte call counts as two queries, one for each half.

**The ground** is [LMN], section 5.1 and Corollary 1, as we read it in the paper. The analysis takes IV xor (parameter block) as a part m0 of the input, which the user chooses freely in every query. It shows that BLAKE2b on (m0, m) is indifferentiable from a random oracle, up to about q / 2^256, if the cipher inside F is ideal in a weakened sense. So BLAKE2b under different salts and personalizations is a family of independent random oracles. **Caveats.** The corollary is for the whole 512-bit output, and cutting it to the digest length is a one-line step of our own. Its proof asserts three conditions of another paper in one sentence. Its simulator makes about q^3 queries, so a strict count does not follow from the corollary alone. Indifferentiability carries over to single-stage games, which soundness and hiding are.

**The format's own routines hash nothing else:** blocks/ and the GPU engine (prover/engine/) compute no hash but H. **The programs around them do, and the assumption above does not cover that.** cp_verify and cp_prove hash some **public** inputs with a second hash mode of our own, built on BLAKE2b's compression function (../../verifier/HASHES.md has the table): with its tree hash TH() (verifier/src/vf_common.h; prover/common/host_common.h) a request's tokens with its two numbers, and the scale file; with its plain hash (H there, under the numbers 72 and 73; TH() is built on it) four public tables and the lists of look-up calls. The statement's words themselves, all but the next token's, go into the first query as bytes. Both hashes call BLAKE2b's compression function F directly, with their number and the list's length in the upper half of its counter, where BLAKE2b has 0 (`older.h` has those modes, and in blocks/ only its own test calls it). So their calls differ from every call that BLAKE2b makes, but they are outside [LMN]'s analysis. No published analysis covers the second hash mode. No attack is known to us.

The nine digests of these inputs then go into the first query of a proof's first chain as bytes. The request file's words also enter that query under H itself, as an item of their own (`the request file's words`: ../frame/check.h, bind_request_statement()): the tokens, then the two numbers. So another request (other tokens, or another range of checked tokens) gives another first query under H, and so does a statement that differs in any other word, or another configuration: the statement's words, all but the next token's (the next token enters the chain in a round of its own), and a digest under H of every byte of the three configuration files, are in the first query too (by a reading of the verifier's code).

What this means for soundness is an argument, and no formal proof states it (../../docs/format/FORMAT.md, R15.3). In short, and at more length in ../../docs/limits.md ("What the bounds rest on depends on the parameter file", under "The hash"):

The second hash mode digests the request file and public data (three lists of lines of the parameter file, the scale file's words, and four tables computed from lines of the parameter file). The request file's own words also stand in the first BLAKE2b query of each proof's first chain beside that digest, and the public files are bound through the commitment ID that the client holds. So, for a prover under a commitment the client already holds, nothing it chooses reaches a challenge through the second hash mode alone. For a prover, then, that mode is used as the fixed, public function that it is, not as a second random oracle; that it does not disturb H's is a weak assumption about the pair (FORMAT.md, 12.6). This is said of each set of public files one at a time, not of a committer that searches for files with the hash in hand. One thing hangs on the second hash mode alone: which four tables, bit for bit, a parameter file names, and so a commitment, since only their digests under that mode stand in the file. A verifier's verdict is about the tables that it computes itself and holds against those lines. Two verifiers, or a definition that takes the tables as data, speak of one function if their tables are the same; that both tables fit the lines shows this only as far as nobody can find two tables with one digest under that mode (its collision resistance: an assumption of such a statement). Take Lean to prove nothing about that mode.

The tables' formulas, with the numbers that they take from the parameter file, do not fix the tables bit for bit, because the programs evaluate them with the platform's exp, pow, cos and sin, whose last bit no standard fixes. So only the file's 32 digest lines fix them (FORMAT.md, 12.6).

The weight table's tree is a stored tree under 174 and 166. A column of R symbols costs ceil((R + 7) / 16) calls.

A hash without a start is plain BLAKE2b-256 of a string that begins with a label. If a program hashes anything else with plain BLAKE2b-256, that input must not begin with sixteen bytes that are a label of this format; the programs of blocks/ make no such hash.

## 3. What a hash costs

A hash of n bytes costs ceil((16 + n) / 128) calls of F. A vertex (80 bytes), a run's value and a hash of nothing cost 1. A leaf of W symbols with a salt of s bytes costs ceil((16 + 8 W + s) / 128); the fill of section 4 costs no call. Compared with a label that cost no bytes, a leaf with s = 40 costs one call more exactly if W mod 16 is 10 or 11, and call 0 of a round does exactly if the number of the prover's bytes is 104 or 112 mod 128. **Rule for whoever puts rows into trees:** no tree's W is 10 or 11 mod 16; an empty row or two avoids it.

## 4. A leaf, the run's value, the salt

A leaf's bytes are the column at its position (8 bytes for each element, in canonical form), then fill, then the salt. **Every leaf has a salt of its own.** None is shared, not even by the leaves over one position of a shorter row whose symbols are copied into them.

**The salt lies whole in the last block** that BLAKE2b compresses: if it would cross a boundary of 128 bytes, zero bytes fill the block before it. So whoever would test a guess of (symbols, salt) hands the whole salt to one call of F, in the block, which keys the cipher inside F. The salt has 40 bytes: that is the value in the library's example parameter file (`../frame/examples/record.f2.txt`) and the least length (one constant in `hash.h`; a parameter file can set 40 to 64, a multiple of 8). It is the textbook commitment: H(data, long random suffix).

**The run's value** is H(172, 0, the chain's label; the parameters' digest, 32 bytes). The 32 bytes are the chain's random bytes from the head of the proof or, for the one chain that all views of a batch must derive alike, the root of the tree that binds the batch's requests. The verifier derives the value in its own run of the chain that sends a tree's root, never takes it from a proof, and rejects a proof in which the run's value is 32 zero bytes. **What it gives:** a guess belongs to one position of one tree of **one run**. Label and start are in the first call of F, and a later call is tied to them through the 64-byte chaining value, up to a collision of two such values (about q^2 / 2^512). For a stored table and for binding leaves the factor "number of tables, or batches, made under one configuration" stays in the hiding term; at 320 bits of salt it does not matter.

**The shape is in the label.** Symbols, fill and salt alone are not one-to-one across shapes (10 symbols with fill, and 14 symbols of which the last four are 0, give the same bytes; so do 3 symbols with a salt of 48 bytes and 4 with one of 40). So a leaf's label holds W and the salt's length. Then (label, column, salt) -> string is one-to-one whatever the shapes, and that costs no byte and no call. The verifier takes no length from the proof: both come from its own shape, which is also bound through the parameters' digest in the start.

## 5. A round of the chain

See FORMAT.md, rules R5 and R6 (its sections 4 and 5). The answer of round i is a sequence of blocks of 32 bytes. Blocks 2 j and 2 j + 1 are the halves of call j = H(162, the chain's label, i, start = the value before; the prover's message; 8 bytes: kind + 2^8 work bits + 2^16 j; 8 bytes: nonce). Without proof of work the blocks are the chain's new value and then the blocks of the verifier's message. With proof of work they are a block with the test bits alone, then the value, then the blocks of the verifier's message. The value and the test bits come before that message's words, so that a rejected word cannot shift them.

**j is in the string's last sixteen bytes**, so the calls of a round share all blocks of F but the last. A program keeps the chaining value after the whole 128-byte blocks of the prover's message (`ChainPrefix`; a library's copy() does the same), and a further call costs one call of F, or two if the word with j ends a block (the number of the prover's bytes is 104 mod 128). A try of a nonce costs the program one compression, or two where the word that holds the call's number ends a block (blocks/hash/hash.h:554-558). That is what it costs these programs. One try in the search for a proof of work can cost a malicious prover somewhat less than one full call of the compression function: the nonce sits in the last words of the last block and the test reads one word of the output, so the work before the nonce and after that word can be spared; by how much at this layout has not been counted. The bound counts each try as one query to the random oracle, whatever it costs to compute.

The plan fixes the **largest** sequence of answer blocks that the verifier's message of a round can need under the cap on rejections (six tries for an element of the base field, then 0; two for an element that must not be 0, then 1); the programs compute the sequence's calls as they need them. So a sum-check round without proof of work costs one call of F (for up to 96 bytes from the prover) unless a word is rejected.

The cap is for the **verifier's** messages alone. The prover's private coins come from another routine with another rule (`../coins/coins.h`: ChaCha20; exactly uniform; rejection without a cap) and make no call of F.

## 6. What this page does not decide

1. No published analysis covers the second hash mode, with which the programs hash the public lists
   (section 2).
2. No strict count of the protocol's hash term with a chain value of 256 bits is known.
3. Whether it matters that 168 and 176 have no start from a digest of the parameters (such a start would cost nothing; 168's digest enters a first query beside that digest).
4. Whether a tree's number is used once in a session, over run, stored and binding trees: for a run's trees it is, by construction in `../iop/context.h`, and for the others this is not stated.
5. The layout of a binding leaf (173).
6. Which bound on an attacker's queries is meant for hiding, and so the least length of the salt.
