# A second implementation of the rule for random values: the headers that a program compiles

The prover derives every private random value from a short key and a name of sixteen words, by the ChaCha20 block function ([../../docs/format/COIN-KEYS.md](../../docs/format/COIN-KEYS.md)). No verifier can see whether such a value is what the rule gives: a proof whose masks are all zero verifies like any other, and hides nothing. A prover that makes a value twice by one routine and compares the two does not see a fault that both share. So the programs work some values out a second time, on the CPU, with the headers of this folder, and compare.

## What is here

A small C++17 library, headers only, with no dependency beyond the standard library. It includes no file of the programs. Only the headers that a program includes are here. What a program holds to them differs from one user to the next, and this page keeps no list: each source that includes one of these headers says at its head what it compares, when, and how the program ends at a difference.

Three of these headers (`chacha_block.h`, `coin_generator.h`, `coin_streams.h`) lie a second time, byte for byte, in `../tests/coins_second_text/`, where tests use them; the twins of the other four are not part of this repository. They lie here because the default build may compile no file from a folder named `tests` (`build.sh`).

## How far it is independent of the programs

Less than its name says. Count an agreement as a guard against a slip in one of the two texts, not as a second reading of the rule. Each point below says with what a part of this library is NOT independent: there the two texts can share a misreading, and an agreement does not rule it out. Whether this library is independent of a file of the programs that no point below names has not been examined: of those files nothing is known either way.

- **On what it rests.** The rule for random values as a protocol document of this project states it (that document is not part of this repository; `../../docs/format/COIN-KEYS.md` states the rule here), with RFC 8439 (ChaCha20) and RFC 7693 (BLAKE2b) as the specifications. The text of `chacha_block.h` and of `blake2b_plain.h` is adapted from public reference code, which each file names.
- **The key schedule and BLAKE2b.** `schedule_keys.h` is not independent of the programs' own key schedule (`../common/coin_keys.h`): it follows the table in that file's head. `blake2b_plain.h` is not independent of the programs' BLAKE2b (`../../verifier/src/vf_earlier_hash_f.h`, `../common/blake2b_f.h`, `../../blocks/hash/blake2b_f.h`): all four are adapted from the BLAKE2 team's reference implementation in C, through the same intermediate texts of this project. None includes another, but what they take from the reference code (the two tables, the rotation, G, a round) are the same statements in all four. The routine around the compression function, which feeds it the blocks and finishes the hash, is shared too: the programs' (`HasherT` in `../../blocks/hash/hash.h`, through which their key schedule hashes its items) is adapted from the reference's `blake2b_update` and `blake2b_final` as `blake2b_plain.h` has them. So in the comparison of the two key schedules the whole hash, not the compression function alone, is one text in two adaptations. So for the key schedule a misreading of the rule, or a slip in adapting the reference code, that is in both texts passes unseen. A slip in `blake2b_plain.h`'s rendering that the programs' routine took over is such a slip. It still shows where it bites in one way of feeding alone (the programs feed the string piece by piece, this library whole), or where a known answer made with Python's standard library meets it: for the key schedule's own strings these are seven keys, from strings of 117 to 347 bytes, none of which ends on a block's border.
- **Eight points of the rule.** On eight points the rule's text follows what both texts do, not the other way round. On these points the two texts agree by construction, not as two readings of the rule. One of the eight matters only with digests of 10 words, which are not built.
- **One known difference.** By the library's own account, where a retry word, or the try word of a leaf's draw, does not fit 32 bits, the library stops with an error; programs that are not the released ones would go on modulo 2^32 there. Whether the released programs do has not been looked at. No run reaches that point.
- **The part that depends on the field.** In `coin_generator.h` the part that depends on the field (which random words are rejected, and the retry) is not independent of `../../blocks/coins/coins.h`, the generator of the proof library that the programs compile: it shares little text with it (the retry loop's bound and its message are the same to the letter), and can share its reading of the rule.
- **The library's own tests.** They compare the library with a table of known answers that was made with the programs.
- **Five conventions of the start-up self-test.** The program that makes the self-test's known answers (`../tests/coins_known_maker.cpp`) writes five conventions out itself, and these are not independent of the programs' lines. An error in these five that the programs share passes unseen.
- **The self-test's cases are no blind sample.** They are not independent of a list of faults that were put into copies of these sources on purpose. That the self-test stops those faults is therefore no blind trial of it.
- **Two outside sources are common to both texts.** ChaCha20's quarter round is adapted from the macro QUARTERROUND of D. J. Bernstein's ChaCha code (chacha-merged.c), and BLAKE2b's compression function from the BLAKE2 team's reference implementation in C, in this library and in the programs alike, on both sides through the same intermediate texts of this project; BLAKE2b's feeding and finishing come from that implementation too, the programs' through this library's `blake2b_plain.h`. So `chacha_block.h` is not independent of the quarter round of the programs' ChaCha20. An error of either source, or a slip in adapting it that is in both texts, passes unseen. The two block functions are different texts around the quarter round, but both go back to that one public reference text, D. J. Bernstein's code in the copy that OpenSSH 9.6p1 carries as chacha.c: this folder's in whole (the copy of the initial state, the round loop and the additions after it follow it too), the programs' in the quarter round and the order of its eight calls. A comparison of the two can show an error made in adapting that reference, or in what the programs have of their own around it; it cannot show an error of the reference. What holds each text to its specification is its known answers: RFC 8439's test vector, and values made in Python.

## What an agreement shows, and what it does not

Where the programs give the library's values, a slip in one text's code is ruled out unless the other has the same slip. A misreading of the rule that both writers share is not seen. Neither is anything about how the programs use a random value: which stream and index they ask for, under which key, and whether the value that was drawn is the value that masks.

The library holds keys only as long as an object lives. Only part of it overwrites its own copies: `coin_generator.h` wipes the keys that it holds, `blake2b_plain.h` its state, and `schedule_keys.h` the last buffer of the bytes that it gathers for a hash; buffers that it outgrew are zeroed only where the program's own `operator delete` does that. By their own comments `schedule_keys.h` wipes no key, `mask_generator.h` wipes nothing, and `chacha_block.h` erases neither its copy of the key nor the block from which it takes a derived key; so copies of keys, masks and blocks may stay on the stack. What a compiler leaves in registers or on the stack is not reached either. It draws no randomness and keeps no record of what was derived.
