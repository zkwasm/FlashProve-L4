# How a run of the prover ends: what is zeroed and what is not

*What this page says comes from reading the source code, unless it says that something was seen. Most runs that it names were made once, on made-up weights†. No run has searched a process's memory after an exit. The page's claims were compared with the sources once, claim by claim, in a text from which this page differs in places: a sentence that is not in that text was not compared. Nor were the sentences that tell of runs or measurements; of the columns "what to do" only the files, options and headings that they name were. That comparison found sentences of that text false; none of them stands on this page in that form. Where this page and docs/limits-all-rows.tsv differ, the rows hold. Not compared, or compared only in part: what clients hear after a 9 ("The three exit statuses"); the row cp-weights-files ("After status 1"); the first paragraph of "After status 9" and the limit on the one-time pads at its end; what NVIDIA's header says ("An exit that cannot zero the GPU"); and the numbers of the routing in launch arguments ("In memory and on disk"). The strip of zeros ("Status 0 after a fault") was not found in the sources.*

## Read this first

*Paths: a path on this page that begins with `docs/`, `tools/` or `scales/` is read from the repository's top; every other path, `../blocks` among them, from `prover/`. Words: status, folder, refuse, stored copy, default build and made-up weights on this page mean what the pages under `docs/` call exit code, directory, reject, [leaf table](../../docs/glossary.md#leaf-table), [production build](../../docs/glossary.md#production-build) and [synthetic weights](../../docs/glossary.md#synthetic-weights).*

## The three exit statuses

They are those of a call of the default build that proves or serves. The call `cp_prove -clear` is apart: it ends with 0, 1 or 2, which the usage text tells, and prints no last line of this kind.

| status | meaning | what to do |
|---|---|---|
| 0 | cp_prove was told to end, every response that it owed has its final file name, and no step of the zeroing failed. It does not show that a proof verifies: `cp_prove` runs no verifier | nothing |
| 9 | one of the program's self-checks on secret random values or keys failed (one of its names, `own-test-coin-library`, can also mean that the operating system gave no memory page that a fork wipes, which needs Linux 4.14 or later: then no self-check has failed). The machine or the program may lose random values, and a proof made with a lost value still verifies but hides less. Nothing that had no final file name at that moment is handed out, with three exceptions, the first two of which arise with `-overlap` or `-overlap-two` alone: a batch whose files are being read for their tags or named at that moment is named to the end; and for a few self-checks, whose result travels as a flag, the release is blocked only once the service has read the failed check's result, so until then an earlier batch's responses can still get their final names; and where the self-check ends the program through exit(), the release is stopped only after the exit handlers that were registered later, so in that time a response can still get its final names | find out why before you start the program again, above all on the same machine |
| 1 | every other ending: a wrong call, a refusal, a fault of the machine, a signal, a normal ending whose zeroing failed, or an ending whose zeroing was given up at its time limit. A few self-checks on secret random values or keys end with this status too, not with 9, some of them with a bare `p258 end 1` | see the name; treat a bare `p258 end 1` as you would a 9 until you know its cause |

Do not let a supervisor restart the program automatically after a bad exit: after 9 above all, but also after 1 and after a kill, so a list of exit statuses is not enough (with systemd: `Restart=no`; docs/operators-duties.md, "Keys, seeds and machines", the row "no automatic restart"). The status, like the last line, is for the operator: a front end should not pass it on to clients. By inference from the code, after a 9 clients with a request in progress hear nothing until the next start (docs/what-is-not-hidden.md, "What a front end must do"). Clients see a service that stays down after a 9 as an outage. Every ending other than 0, not a 9 alone, can withhold the one earlier batch that is staged and not yet named, though it was proved whole; no ending, a 9 neither, takes back what has its final names; the next start removes of it only what was not yet synced (docs/limits-all-rows.tsv, row C3); for none of these events is a probability bounded anywhere (docs/limits-all-rows.tsv, row HW-583).

After every ending other than 0, the requests of a spool directory that were taken and have no response stay in `work/`. The next start answers each of them `failed`; the clients send them again. With `-in` and `-out` there is no `work/`: the requests stay in the folder of `-in`.

## The names in the last line

The default build prints ordinary sentences until the line `p258 closed: ..`. A refusal before that line comes with a sentence that says what is wrong and, in most cases, in brackets, its name. After that line the program says of its end only `p258 end <status> <name>`. The name is a fixed word. It says which check or which fault ended the program, and never carries a value, a place, a count or a request.

`p258 end 1` without a name means an ending for which the program has no name: an internal stop that is not listed here, one of a few self-checks on secret random values or keys (the table of statuses, above), or a crash (SEGV, BUS, FPE, ILL, ABRT, SYS, TRAP), after which nothing was zeroed. One such internal stop: cp_prove does not take a part of a weight tensor that has more than 33,025 rows and is read through the row pass over blocks: that pass takes five of the seven stored types, Q4_K, Q5_K, Q8_0, F16 and BF16 (the last two are not quantized), not Q6_K or F32. It finds that out in the middle of a proof, not at its start, and ends with status 1; a [test build](../../docs/glossary.md#test-build)'s sentence begins "internal error in the row pass over blocks", though the program is not at fault, and the default build shows no sentence. A crash that comes after a name was set prints that name, so a name does not rule out that the program crashed afterwards and skipped the zeroing.

After one failed self-check a test build also prints a count that depends on hidden memory (how many cells of the sub-proofs' masks agreed); a test build runs on made-up weights alone, and the default build's output is closed by then and shows no such line. That self-check is not the only one. In cp_prove and in cp_commit the self-checks by value (among them `hold()` of hiding/engine_coins.cuh; the seams of an opening, hash_commitment/hf_open_side.cuh; the second writing, second_writing/) compare hidden values made twice and, where they fail, print counts, a self-check's number or a fixed sentence, no value. cp_commit closes its output in no build, so its default build prints such lines too.

## How an end goes

- **What has run.** The default build (`./build.sh` with no target word) has run at small configurations, some ends behind its closed output among them (the suite's rows that use the serving build). For most kinds of end it has not been run: there the page tells what the sources say. Nearly every run, those under a randomly drawn seed too, was a test build's, which prints each failed request's cause and flags (prover/service.cuh, `end_the_batch()`).
- **Guards.** Code of the proof library (../blocks) and of the GPU engine (engine/) ends the process at any of some 850 guards, each with one line on standard error: file, line and a sentence. cp_prove then ends as at every other end: the wipe, staged files overwritten and removed, the last line (`p258 end 1` with the guard's own name, if it has one, else `guard`; once its output is closed, the default build does not show the guard's own line), status 1, or status 9 where the name is that of a self-check on secret random values; the whole batch is lost. A failed CUDA call of the engine ends in the same way, under the name `cuda-call`.

  The wipe is not whole at every guard: an exit while the service's thread is inside a call of the code that holds the weight table leaves out that code's own erasing ("Exits that skip the zeroing", below). A test build's last line says so ("every step of the wipe ran: 0"); the default build says so in a line before its last (`p258 not every step of the wipe ran: ..`). Some ends do not take that way and call `abort()`, so that nothing is zeroed: `PSC_STOP()` on the host (hiding/psc_device.cuh); the four in hash_commitment/hf_mask_ref.h; a guard before `arm_ends()`; a guard that fails inside a wipe that a guard has begun; a library's; and a crash of the program itself. By the sources the default build then catches the signal and ends `p258 end 1`, with the name if one was set before, and status 1, or 9 if that name begins `own-test-`; if the program has begun to read its secrets, the line before it says that not every step of the wipe ran.

  A partial reading† of the code found no guard that ends an honest run for some weights and not for others, unless a value leaves its range; it has not been shown that the end of a process tells nothing about the weights (docs/limits-all-rows.tsv, row HW-256, says what that reading covered).
- **Status 0 speaks of the wipe's steps, not of all memory**, and so does a test build's "every step of the wipe ran: 1" at a bad end. The engine's memory comes from a CUDA pool that is on none of cp_prove's lists: no exit wipes it, the good one neither, and a request's tables, mask rows and salts stay there. The other threads run until `_exit()` and can write behind a step that has zeroed, on the host and on the GPU; what they make from then on gets no name in `out/` (prover/ends.h, `g_end_first`), but it lies in memory.
- **One exit gets a false cause.** A test build reports `exit(1)` as cause 9, a failed CUDA call (the default build's last line has no cause's number); some internal errors end so too. The status is 9 exactly where the end's name begins `own-test-`, whatever number the source hands to exit(); the first name that is set stays, so where a failed CUDA call has named the end first (`cuda-call`), a self-check that fails in the same moment ends with status 1 and not 9; an internal error whose source says exit(4) or exit(2), and that sets no name, is seen as status 1.
- **An honest failure can be charged to the machine.** At some places a value that leaves its range, which depends on weights and prompt, also raises a self-check's flag: a test build's line for the request then gives cause 20, which stands for a fault of the program or the machine. What is meant to keep a value from leaving its range at all is cp_commit's worst-case check; that it suffices is an argument, not a verified proof.
- **cp_commit catches five signals: SIGABRT, SIGINT, SIGTERM, SIGHUP and SIGPIPE** (one of the last four that was ignored when the program started, as under nohup, stays ignored). At each, from the moment when the cleanup is armed to the run's good end, it removes everything that the call has made, by name; a signal after the good end's last step removes nothing, and a whole commitment stays on the disk. This also holds of directories that already have their final names: until cp_commit has ended, the secret and the public key folder can appear and then be removed again, so use neither before cp_commit has ended with status 0.

  A file that the call has created is overwritten with zeros and synced before its name goes, those of at most 32 bytes (the seed and the other secret byte strings) first; a file that cannot be overwritten keeps its name. Removed without zeros, and without a word: what has a second hard link or is no regular file, what cannot be examined (that may also be left), and a file whose device and inode numbers are no longer those that were noted when it was made; and a listed file that another hand has moved away from its name is not overwritten at all. What goes without zeros stays in the file system's free blocks, or under its second name if it had one. The overwriting takes seconds for each gigabyte, so a SIGKILL that follows the first signal after a short grace time can leave large files and both working folders behind. It prints one line, which says so if not all could be removed, and dies by the same signal (status 134 after SIGABRT, 143 after SIGTERM).

  One stretch is not closed, by the source's own word: at an abort, or a signal that the system hands to another thread, while the main thread is in the middle of a write, a file or a new name can appear after the cleanup has passed. The keys in memory are not wiped on that path, and the program does not wait for the GPU first: a kernel of its own may still be running when it dies.

  SIGKILL, any other signal, a crash or a power failure leaves what was made, under `<isk>.making` and `<ivk>.making` (between the two last renames: `<isk>` and `<ivk>.making`), with the seed in the first. The same call, made again, is then refused; where only the two working directories are left, the refusal says whether a cp_commit is still running in them and which two directories can be removed (docs/faults.md, "A killed or failed cp_commit").

  A file made under `-worst-case-table`, which is computed from the weights, is removed by a call that fails, at these signals too once the cleanup is armed; it stays at the good end and at status 7, where it is the answer that the operator asked for, and after SIGKILL, a crash or a power failure. Not reached: an exit, an abort or a signal before the cleanup is armed. Until the check writes its table, that leaves an empty file; from then to the making's start, a short stretch, it leaves part or all of the table. So the file that stays behind can be empty, partly written or complete: keep it as secret as the weights (docs/faults.md, "A killed or failed cp_commit").
- **One condition of hiding is checked by a test, not in a run.** That no generator of random values is made twice under one key is the caller's duty, and nothing checks it in a run. In cp_prove all generators of a batch are made at the batch's head, where the batch's key is derived and its object wiped (its bytes stay in two other places, which the batch still needs, until the batch's own passes are over); after the head no routine is handed the key. That layout is checked by a test that reads the sources (not in this repository), not by the compiler; that test does not cover the copy of the key in prover/slot_pads_second.cuh. GPU tests list the generators in the runs that they make: a test build, a test seed, small configurations; at full size there is no such run.

## Status 0 after a fault

Status 0 does not say that every GPU kernel ran. In trials†, one kernel launch was made to vanish without an error, at small size and at full size. Runs of cp_prove ended with status 0 and released proofs that the verifier accepted. There, padding cells that should hold 0 held bytes left by the step before, some of which depend on the weights. No written claim about hiding covers such a proof.

In like trials a strip of zeros with no blinding of its own, 1.5 MiB a request at full size, had part of its launch left out at small size, or all its zeros at full size: the service released proofs over stale bytes, and the verifier accepted them. One more buffer's zeros rest on a single launch.

For the padding cells the programs count the zeros before committing, in twelve matrices only, not in the two that hold the residual stream: a short count fails the request; a later write, or several losses at once, can pass it unseen. Other kernels were not examined.

Self-tests end some runs that would make their secret random values wrongly, and do not show that anything is hidden. Whether they would stop zeros in some of a row's positions for such values has not been tried on the released programs.

## What an exit gives away

cp_prove's rule: a failed check on a hidden value neither ends the process nor changes its status; the request, or its batch, is answered "failed". It has exceptions, and no list gathers them.

- A test build (`./build.sh tests`) prints which such check failed and each failed request's cause. The default build (`./build.sh` with no target word) lets none of these out: it prints fixed lines, one line a batch with public numbers only, and a final status line.
- cp_prove runs no verifier: nothing in it tests a finished proof as a whole. A proof that a verifier would reject gets its final name like any other, and the service goes on; whoever hands a response on must run cp_verify on it first (duty 6: docs/limits.md#the-conditions).

  A verifier does not stop everything: a faulty file that it accepts, a lost mask for one, passes. And it can be wrong the other way: cp_verify says `NO` if it cannot read the leaf file that the proof names or finds no layout.txt, and it rejects an honest proof at a few rare events on hash output.

  **What has run** (the suite's row `gpu.serving_first_run`): on the default build, at a small configuration, on made-up weights, on one GPU: the row passed; its script asks that, with one bit of the secret folder's leaf file flipped, `cp_prove` end with status 0, and that `cp_verify` accept the response under the published leaf file and say `NO` under the altered one. Not seen in a run of the default build: `cp_verify` ending `NOT CHECKED` on a service's response; any rejection at full size of a response as `cp_prove` wrote it.
- Whoever can write the secret folder, client or not, can undo every safeguard stored in it. Whether such a writer also learns about the weights from how each start ends has not been examined on the released programs: take it to hold (one trial†: docs/limits-all-rows.tsv, row H46.4).
- The folder counts the columns that begun openings show, because each stored table's random entries bear only a set number. (A test build's cp_prove prints a line for each leaf table at its start: columns shown, columns that it bears, columns a batch shows, batches left; the default build prints none: docs/operators-duties.md, "Renewing before the number", says by what to plan.) A copied or restored folder counts for itself, unseen by any program, so masks can be used past that number.
- A model file whose header declares more data than it holds can lead cp_commit's parser on into the tensors' bytes: where the run then ends, and the entry's number in the line that it prints on standard error, depend on weights' bytes. The line holds a fixed sentence, the file's path and that number, and no name or string that was read. cp_prove's default build shows of it only `p258 end 1 cp-weights-files`; a test build refuses a model's files.
- Whether memory runs out or a write fails can depend on hidden values. Whether a failed check changes a batch's time has not been measured.

- A reading of the weights from how a start or an end of the service goes gains with every start of the service (in one trial† about 32 starts gave the magnitudes of two weights: docs/limits-all-rows.tsv, row H46.4), and so does the leak by the line `weights` of `isk.txt`, which no check at a start stops, so a supervisor that restarts by itself serves such a reader. (The duty: [../docs/service.md](../../docs/service.md#how-the-service-ends), "How the service ends": do not restart the service from a program.)

## The committing program has no such rule

cp_commit ends where a cause is found, and some causes depend on the weights, on the seed or on sampled values. Its status, its lines, its timing and what it leaves on disk show them; what many runs together show has not been examined (docs/limits-all-rows.tsv, row HW-555). Whoever can write the two unsigned files beside the model and see the outcome learns, among other things, each tensor's largest product of weight and gain to within a factor of two.

Its cleanup overwrites the seed and the keys in host memory, though not copies on a routine's stack, and removes what the call has made ("How an end goes", at the five signals); a file that is taken back after a failed write is overwritten too. On a disk or file system that writes a changed block elsewhere, as flash does, the old block can outlive the overwrite. With several threads the cleanup walks its list twice, which catches a late writer mostly.

A direct exit, and some other failed ends (a refused model among them), leave weights, values computed from them, or masks unzeroed on the GPU and in host buffers; also the rows' pads. While a weight table is made, all its rows' pads lie in GPU memory and in host memory: both copies are zeroed where the making closes and before a failed self-check `own-test-masks` or `own-test-pads` exits. While the record's answers are made, a further copy lies in host memory: it is zeroed when that routine returns and before a failed self-check `own-test-pads` exits. While a table is opened for the key file or a leaf file, the pads are derived twice more, once in host memory and once in host and GPU memory: each copy is zeroed as its use ends. No other exit zeroes any of these, not even the one by which cp_commit's comparison of masks, salts and keys with its second implementation (second_writing/) ends the run when it fails. The host copies lie in ordinary, unlocked memory, and by hf_pads.cuh's comment copies to and from the GPU pass through the CUDA driver's staging buffers, which no code of the program zeroes, at the good end neither. The host memory that holds the model's tensors is overwritten at no exit. At the five signals the keys in memory are not wiped; at an end by the program's own status they are, after the removal. SIGKILL, any other signal, a crash or a power failure ends it with nothing wiped and nothing removed.

## An exit that cannot zero the GPU

After a kernel's illegal memory access or trap every later CUDA call fails, the zeroing too. For an illegal address NVIDIA's own header says as much, in its note on the error code cudaErrorIllegalAddress (driver_types.h of CUDA 13.0; the header of CUDA 13.2 was not looked at). Weights and masks may then stay on the GPU. A test build then prints `fork memory: GPU memory could not be zeroed; weights and masks may stay on the GPU until its memory is reused or the GPU is reset` (prover/fork_memory.h), and its last line says `every step of the wipe ran: 0`. The default build's last line does not tell its operator that; by the code, a line before it then says that not every step of the wipe ran, and not which, wherever the program can still print. Where the fault is first met inside a call of the code that holds the weight table, the exit is also one of those at which that code's own zeroing is skipped (the next section's third point): its secrets then stay in host memory too. When refusals of kernels were forced for lack of memory, about one in six† of the prover's exits reported GPU memory not zeroed; whether by an illegal access is not known. Whether a reset of the GPU, or a reboot, clears that memory has not been examined, so this page asks for no such step: give the GPU, and the machine, to nobody else. What another process can read there has not been tried.

## Exits that skip the zeroing

- A KILL, or another uncaught fatal signal, zeroes nothing and prints no final line. In the default build a crash signal zeroes nothing and prints the last line; if the program has begun to read its secrets, the line before it says that not every step of the wipe ran. In a test build the signals QUIT, ALRM, USR1, USR2 and PIPE, and the others that ask a process to end but TERM, INT and HUP, skip the wipe altogether, unless they were ignored when the program started: that build does not catch them. One direct exit would skip the wipe altogether, and the last line with it: an `_exit(23)` in hiding/door.cuh (`close()`), in an exit handler that is registered only if a sub-proof is closed while no closing function is installed; the set-up installs that function before the first request, so by the sources it is not reached.
- A second thread that asks to exit while an exit is under way waits for the end that has begun (prover/ends.h, `end_on_exit()`).
- An exit that comes while the service's thread is inside a call of the code that holds the weight table skips that code's own zeroing, on whichever thread the exit began. That thread waits inside such a call while the part of a proof that a batch's requests share is made, so a check that fails there ends so. What then stays in host memory until the process is gone: the key from which the masks, the salts and the pads of the leaf table in use are made (32 bytes, twice), and the rows' combination u, an exact linear image of the weights, of the masks and of the pads. Pads already made from that key stay at every exit ("In memory and on disk", below). The GPU memory that this code was lent (the sub-proofs' scratch memory and the weight stream's GPU buffers, in both of which copies of weights lie for a while, and, with `-overlap`, a buffer that cp_prove allocates for that part) is zeroed by the wipe's next step, if CUDA still responds and the wipe is not given up at its time limit. The thread that is still inside that code can write to this memory again afterwards, and the GPU memory that the part allocates for itself at set-up is zeroed at no exit. A test build's last line then says `every step of the wipe ran: 0`; the default build prints `p258 not every step of the wipe ran: ..` before its last line.
- A zeroing that has not finished after 600 seconds, as when the GPU no longer answers, is given up, and the program ends. The limit does not help while the program's main thread sleeps uninterruptibly in the kernel (a dead driver, a hung disk): the process then hangs and prints nothing until it is killed. After status 9 the last line does not say so: the line before it does, and so do the ten minutes before it.

## In memory and on disk

Before it exits, cp_prove zeroes the secrets of the code that holds the weight table, the GPU and pinned buffers on its own lists, the keys and the seed. These are on none of its lists and stay after every exit:

- The copy of the weights in pinned host memory.
- Each thread's page-locked buffer for uploads to the GPU (32 MiB a thread), which is never cleared and which, by its source, is meant only for lists that are no secret, a rule that the source names no check for.
- The memory of CUDA and its libraries, launch arguments included. Where a routed experts' tensor is stored in 8 or 16 bits (Q8_0, F16, BF16; read in the code, which goes by each such tensor's own stored type, not by the file), these arguments carry numbers of the routing, which is a hidden value. One-time masks reach the GPU by a plain copy from ordinary memory, which the driver may stage in pinned memory of its own; whether the driver does stage them has not been looked at. Not all host copies of private random values are wiped: by engine/device.cuh, what `samples()` returns, vectors local to a call and a tree's mask rows are not, so an exit can leave them.
- During a batch's opening, in ordinary host memory that no exit zeroes: one exact sum for each row of the weight matrix, and the opened columns' words. A record's pads reach the GPU through pageable memory.
- The stored hash-tree nodes of the leaf table that was used last, in pinned host memory of the code that holds the weight table: digests, which are also in the secret folder.
- Whatever only a destructor clears: cp_prove leaves by `_exit()`, which runs no destructor. So the random generators' own copies of a key in host memory, and GPU tables that are derived from the weights and that only a destructor zeroes, stay, if the object is alive at the exit, unless a step of the wipe reaches them.
- The pads of the leaf table in use: during an opening they lie in an ordinary host buffer that no step of the wipe reaches, also at an exit at which every step of the wipe ran (at a bad end a test build's last line then says `every step of the wipe ran: 1`; the default build prints no line `p258 not every step of the wipe ran: ..` before its last; inferred from the order of the code's lines, not seen in a run). With the published answer of the record that it masks, a pad gives one exact equation on a row of the weight table.

An exit in mid-batch leaves each live request's tokens, answer and proof data in host memory. An exit during the last step of a batch's opening leaves that step's one-time masks there, beside the values before masking. Ordinary host memory can reach swap.

At an exit, staged answers and proofs on disk are overwritten with zeros and then removed (only a regular file of this user's with one name is written into: a link is not followed); what a file system or a disk keeps of overwritten blocks is beyond the program's control. If a lock cannot be taken in time, and after a kill or a crash, they stay whole until a next start on that folder whose requests have the same length as those left in `work/`, for any commitment, which overwrites and removes what it can. A proof that a verifier refuses can hold what it is refused for, by one reading an exact linear form in the weights, so such files are secret too, and they can stay on disk.

In an honest run too the proof library itself frees host memory that has held random values (mask rows, random tails, old one-time pads) without zeroing it; in `cp_commit` and `cp_prove` replacements for the global operator new and operator delete zero each block when it is freed, not before (common/zeroing_heap.h; no run has looked at a program's freed memory). Not covered, by that file's own comment: blocks allocated directly with malloc() or aligned_alloc(), what precompiled code of the C++ standard library allocates and frees, and blocks not yet freed when the process ends; nor anything on a stack or in page-locked memory.

The zeroing of GPU memory goes by the status that each CUDA call returns and never reads the memory back, so a call that reported success without having zeroed would go unnoticed; the code's test modes that count bytes left over do not cover the zeroing at an exit. The list is not complete.

## How long an exit takes at full size

At the end of a full-size cp_commit or cp_prove the process took about half a minute† to exit (5 to 8 seconds† with `-huge-pages`, on a test build). In one full-size run two separate callers of `nvidia-smi` gave it up as stuck, one of them after a KILL had not ended it within 5 seconds; by the counts of its looks the other falls in cp_commit's exit. No Xid, no ECC count, no alarm. Seen once; the cause is not known.

## The three alarms

Three more lines can come between `p258 closed` and the last line. Each is constant, is printed at most once in a process, and ends nothing: the service goes on. With the first two no request loses its response; the third says that a request waits without one.

| line | what it means |
|---|---|
| `p258 alarm memory-grew: ..` | the prover's own GPU memory has risen above its peak at the end of the first pass, by which it is meant to hold all that it will ever hold |
| `p258 alarm cut-short: ..` | `in/` holds more requests than one scan reads, so the requests that are served need not be the oldest |
| `p258 alarm unreadable-request: ..` | `in/` holds a file with a request's name and length that the system does not let `cp_prove` read (`Permission denied`) |

All three are for the operator alone. Whether cut-short comes depends only on the number of files in `in/`, that is, on the clients' load. Whether memory-grew comes depends on how many requests a pass holds compared with the first pass. A limit: that it does not also depend on how tokens are routed to experts, and so on weights and prompts, has not been shown (prover/fork_memory.h).

**After unreadable-request.** The line is about a file that a scan of `in/` has tried to open and the system has refused (`EACCES`). `cp_prove` has read nothing of such a file, so it neither moves nor removes it, and nothing appears in `out/` under its name. The usual cause: a front end or a command that ran as root or under `sudo` wrote the file with a mode that closes it to the account that runs `cp_prove`. The line names no file. `ls -l` on `in/` shows each file's owner and mode; in the spool directory, as the account that runs `cp_prove`, `find in -maxdepth 1 -name '*.req' ! -readable` (GNU find) lists the files that it may not read. Where `ls -l` shows nothing wrong, the refusal comes from an access list, a security module or a network file system. Once that account may read the file, a running service's next scan takes it like any other file there, and nothing needs a new start. `cp_prove` does not remove a file as long as every scan finds it closed in this way; a clean-up of your own that deletes old requests does. While it stays, a front end that counts the `.req` files in `in/` counts it as waiting: integrations/proof_middleware.py does, and when their number reaches its limit `max_waiting`, replies get no proof.

- The line is printed once in a process. A later file of this kind, also one that comes after the first was put right, is announced by nothing: only `in/` shows it.
- With `-end-when-empty` the service still ends with status 0 while such a file is in `in/`, as it does with a file of a wrong length; the next start finds the file and prints the line again.
- Silent in the default build: a request that was moved to `work/` and then cannot be read there, because the disk fails (`EIO`), memory or file descriptors run out (`ENOMEM`, `EMFILE`, `ENFILE`), the read comes back short, its permission was taken away after the scan had tried it, or the file is closed to the service and the scan did not find that out: its try failed with an error other than `EACCES` (`EPERM`, for one; `ENFILE` for a moment, also on a file that earlier scans found closed), or the file is the service's own account's and has the owner's read permission, so the scan did not try it. It is removed without a response, as a file is whose name is not the hash of its bytes: its name cannot be checked, so no "failed" may appear under it. The line that counts such files goes to the standard output, which is `/dev/null` by then.
- That `cp_prove` prints the line has not been seen in a run.
