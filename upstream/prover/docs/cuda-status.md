# The CUDA error status: the check before output leaves the process

Why every host thread that launches a GPU kernel reads its own CUDA error status before anything that the kernel helped to compute is passed on. Comments in the sources point here. A path on this page is relative to prover/.

## The rule

A kernel launch written with `<<<...>>>` hands nothing back to the code that made it. If the driver turns the launch down, the only trace is in the CUDA runtime's error status, and that status belongs to the host thread that launched. Our threads fetch it with `cudaGetLastError()`, which also clears it; no other thread can fetch it for them, and a thread that does not ask never learns of the rejection. These properties are NVIDIA's, not ours to show: NVIDIA, CUDA C++ Programming Guide, "Error Checking" (docs.nvidia.com/cuda/cuda-c-programming-guide); CUDA Programming Guide, "Intro to CUDA C++", "Error Checking in CUDA", "Error State" (https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html); CUDA Runtime API, cudaGetLastError() (docs.nvidia.com/cuda/cuda-runtime-api).

So a rejected launch of that form sets none of the prover's failure flags and does not end the process. The memory that the kernel was to write stays unchanged. Where that is a row's masks, a salt or a pad, the file made from it can show what it is built to hide, and a verifier may accept it or reject it: neither tells. Hence the rule:

**No byte that a step on the GPU helped to compute is passed on towards a release until every host thread that launched a kernel for it has read its own status, after its last launch, with `CK(cudaGetLastError());` (in the engine: `ENGINE_CK(cudaGetLastError());`). No read of the status lets the process continue after an error: each read ends the process if it finds one.** (The compiler's sample, compiler_sample.cu, is a program of its own that holds no hidden value; it goes on after its read.)

The second sentence of the rule is needed because a read resets the variable. A read that let the process continue would clear the error before a later read could find it. A read is not the only call that was seen to reset the variable ("A call that resets the status", below).

A process that ends drops what it has staged (`drop_what_is_staged()` in prover/spool.h), so a rejected launch costs the batch and shows nothing, provided that the rejection shows in the launching thread's status and stays there until that thread's read. That it shows there is taken from NVIDIA's passages above; for one kind, GPU memory that runs out at a kernel's first launch, it was not tested, and no text of NVIDIA's is known to say so. A rejection that did not show in the status would pass every read, and with it the macro of "A call that resets the status", below. That it stays there is assumed ("An assumption", below); across one call of the CUDA runtime it does not stay, and the programs read the status directly before that call. Staged responses are removed by the process as it ends or, if it does not get that far, by the next process that opens the spool directory (`open()` in prover/spool.h), which overwrites and removes what cp_prove itself staged. What a rejected launch can leave behind on the GPU is another matter. Leaks that are known even without any fault are named in [what-is-not-hidden.md](../../docs/what-is-not-hidden.md).

Every nvcc line of both programs names the shared CUDA runtime (build.sh: `-cudart shared`), and the code that holds the weight table is one translation unit, compiled once and linked into cp_prove as three objects, each with its own copy of every function and static object; so a thread has one error variable for all of a program's code. That unit's own sources read the status themselves. The read also finds the error of a runtime call whose own return status was ignored, if nothing has reset it since.

**An assumption.** Calls to cuBLAS and cuBLASLt occur between a launch and its thread's read. The rule assumes that such a call does not reset the thread's error variable. It also assumes that no call of the CUDA runtime or of the driver does, apart from a read of the status and from cudaFuncSetAttribute() ("A call that resets the status", below). The cuBLAS manual does not say the first: it mentions neither cudaGetLastError() nor cudaPeekAtLastError().

A process can hold several copies of the runtime, each with a status of its own, for instance where a library brings a copy of its own along (CUDA Runtime API, at both functions). The assumption's first half, on the two libraries, was tested on one machine (an H100; CUDA 13.0, cuBLAS and cuBLASLt 13.1.0, driver 570.195.03)†. libcublas.so.13 and libcublasLt.so.13 import no symbol of the runtime, so they cannot reach the programs' instance of it. A rejected launch was followed by each call to the two libraries that the programs under test made, as a first and as a second call, on two threads. The error was still set afterwards in 64 of 64 trials. That test did not cover other versions, rejections of another kind or the runtime's own calls.

**A call that resets the status.** On CUDA 13.0, the one version that was tried, a `cudaFuncSetAttribute()` that succeeds resets the calling thread's error variable. No text of NVIDIA's is known to say so. A rejected launch that stands before such a call on the same thread, with no read between the two, would therefore go unnoticed: the reads that the rule asks for would all be made, and they would find nothing. So the programs make the call through one macro only, `CK_ATTRIBUTE(...)` (common/common.h), which has `CK(cudaGetLastError());` directly before the call; the engine that they share (engine/) has a twin of it in its own words, `ENGINE_CK_ATTRIBUTE(...)` (engine/device.cuh), with `ENGINE_CK(cudaGetLastError());` directly before the call. The read is of the calling thread's variable, which is the one that the call resets.

On one machine (an H100; CUDA 13.0, with the runtime once as the shared library 13.0.96 and once linked statically; kernel module 570.195.03 with libcuda 580.173.02)†, a test program of its own, which is not part of this repository (what it misses: ../docs/limits-all-rows.tsv, row T11.4.1), followed a rejected launch by each function of the runtime and of the driver that the sources called by name. `cudaFuncSetAttribute()` on the launching thread reset the status in 16 of 16 trials in each form; made on another thread it left the launching thread's error in place; and apart from the read itself no other function that was tried reset it (in one row, the end of a capture into which the rejected launch went, the call itself fails and leaves an error of its own in the status). Not tried: `cudaGetErrorString()` and `cuGetErrorString()`, which are called when a process is about to end, and the calls to cuBLAS and cuBLASLt. common/local_memory.cuh reads the status directly before `cudaFuncGetAttributes()`, whatever that call does to it.

No way for a client to cause a rejected launch is known. In runs† no natural cause has been seen to produce one, but one is known in kind: GPU memory that runs out when a kernel's code is first loaded. In a small example† it did not make the driver reject the kernels that were watched; it has not been tried on the released programs. Of the two kinds of rejection that are known, a block that is too large and a launch of too many rows, only the first has been tried. Whether a client can cause a silent loss of a GPU write or launch has not been examined.

† Not on the released programs. What it ran on, and how far that speaks for them: [what was run on these programs, and what was not](../../docs/limits.md#what-was-run-on-these-programs).
